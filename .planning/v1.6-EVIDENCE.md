## Verdict

**REPRO-01:** CLOSED ✓ — uno verdict PASS captured (3 byte-identical 64KB reads; SHA-256 `8d2124eb7c994f717ace1b2b79c52fa95153aa82c6a4891a323ad924ef409759`). **Unexpected — refutes the pre-existing-bug prediction on the Plain Uno (ATmega328P + USB-to-UART bridge code path).** Combined with the uno328pb correction (board was actually a Plain Uno + wrong FW, not a true 328PB), the v1.6 read-bug premise narrows: the jitter is NOT a shared-transport bug across all 3 controllers — it's specific to the Leonardo path (32U4 + native USB-CDC + 1024-B buffer).

**REPRO-02:** CLOSED ✓ — leonardo verdict FAIL captured (3 distinct SHAs across 3 consecutive 64KB reads; 1349 / 65536 bytes diverge between run_1 and run_2 = 2.1% byte-jitter rate; first divergence at offset `0x0003`). Jitter reproduced — the read-bug exists on the Leonardo and is therefore the primary Phase 27 RCA target. Suspects: 32U4 USB-CDC implementation (vs the 328P's external USB-to-UART bridge), 1024-byte DATA_BUFFER vs Uno's 512-byte buffer, or 32U4-specific timing in the per-chunk send code path.

**REPRO-03:** CLOSED ✓ — diagnostic CLI `firestarter dev consistency-check <chip>` shipped in Plan 26-01 (firestarter_app sub-repo commit `999c3cc` on `v1.6-read-bug`, cut from `beta` at `3.0.0b4`). 8 pytest cases green (test_consistency_check.py), full sub-repo suite 90 passing.

### Scope changes captured during the bench session

1. **The board previously called `uno328pb` is actually a Plain Uno + wrong FW.** The v1.5 bench notes incorrectly labeled it as a 328PB-Uno; operator clarified 2026-05-21. The 2026-05-21 baseline data attributed to "uno328pb" in `.planning/todos/pending/large-read-data-jitter-uno328pb.md` (~57.8% divergence) was captured on a FW-mismatched plain Uno — that divergence rate is NOT comparable to the live 2.1% jitter measured on the Leonardo. Phase 27 RCA scope should NOT use the 2026-05-21 baseline magnitude as ground truth for either silicon configuration.

2. **Leonardo W27C512 chip ID variant mismatch (cosmetic, separate from read-bug).** The Leonardo's W27C512 reports chip ID `0xda01` whereas the database entry expects `0xda08` (Plain Uno's chip matched the DB). This is a stable read (same value across all 3 reads), so it's a chip-variant database alias gap, not jitter. Follow-up: add `0xda01` to the W27C512 entry's accepted chip-id list, OR add a separate "W27C512 (variant 0xda01)" entry. Out of v1.6 scope.

3. **Pre-existing `firestarter info <chip>` crash** (`TypeError: '<=' not supported between instances of 'list' and 'int'` at `ic_layout.py:167`). Unrelated to v1.6; flagged for future cleanup.

4. **`Board: unknown-board` cosmetic bug in consistency-check stdout.** The diagnostic's `FirmwareManager.check_current_firmware()` call returned None for board name on both Uno and Leonardo. Non-blocking for the verdict (the stdout regex contract for Phase 29 doesn't include the Board cell), but worth a follow-up patch in Phase 28 or as a post-v1.6 polish.
