# 53-04 / XACT-02 fault-injection — bench findings (2026-06-05, operator-witnessed)

Board: Uno /dev/ttyACM1, W27C512 (id 0xda08), Rev 2.0, post-55 fw (OK: FW: 3.0.0b6:uno).
Harness: firestarter_app commit 630fafd (53-04 false-negative fix).

## Matrix (all 4 combos)
| direction | fault-form    | fault fired | recovery byte-exact | error mode                    | latency* |
|-----------|---------------|-------------|---------------------|-------------------------------|----------|
| outgoing  | corrupt-crc8  | YES         | PASSED              | connection rejected (no ack)  | 6.17s    |
| outgoing  | drop-delimiter| YES         | PASSED              | connection rejected (no ack)  | 23.29s   |
| incoming  | corrupt-crc8  | YES         | PASSED              | CRC mismatch -> Timeout       | 4.43s    |
| incoming  | drop-delimiter| YES         | PASSED              | CRC mismatch -> Timeout       | 4.49s    |
*whole-cycle (includes connect); outgoing further inflated by multi-port connect-retry.

## Verdict vs XACT-02 truths
- "corrupted host->fw frame surfaces a clean error" — PARTIAL: the firmware does NOT ack a corrupt
  frame (no silent accept), but the surfaced error is connection-level / timeout-mediated, not a
  sub-second per-frame NAK. (Measurement also contaminated by multi-port connect-retry — see caveat.)
- "next transfer on the SAME open connection byte-exact" — for INCOMING: YES (same connection,
  recovered). For OUTGOING: recovery is a FRESH connection (the corrupt setup frame fails the
  connection), so "same open connection" does not strictly apply to the outgoing leg.
- "mutated fw->host frame triggers host resync, next frame clean" — YES (CRC mismatch detected +
  recovered). [PASS]
- "both fault forms exercised" — YES. [PASS]
- "sub-second clean error, NOT a 2 s cascade" — NOT MET: errors are timeout-mediated (~2s+). [FAIL]

## Net
Resync DETECT + RECOVER is proven in both directions and both fault forms (the safety property:
serial corruption cannot silently corrupt data). The SUB-SECOND clean-error property is NOT
satisfied — corrupt/dropped frames surface via a ~2 s timeout, not a fast firmware NAK. 53-04
is therefore NOT a clean XACT-02 pass on the current firmware.

## Recommended follow-up (transport, not harness)
To meet "sub-second clean error", the firmware likely needs to emit an explicit fast error/NAK frame
on CRC8/COBS failure (instead of relying on the host read timeout). Alternatively, re-scope XACT-02's
latency claim to "detect+recover proven; bounded error within one host-timeout window". Operator/
transport-owner decision. Per-frame latency should be measured precisely (not whole-cycle) if the
sub-second claim is pursued.
