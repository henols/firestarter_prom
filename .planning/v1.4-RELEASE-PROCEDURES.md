# v1.4 Release Procedures

This document is the operational checklist for cutting a coordinated v1.4 beta release across
both Firestarter sub-repos (`firestarter_app` and `firestarter`). It is built on top of
`15-LOCKSTEP-PROCEDURE.md` (consumed verbatim where applicable), with corrections to that
procedure's stale workflow filenames and additional v1.4-specific verification and promotion
steps. A release engineer with no prior v1.4 context should be able to cut a beta by following
this document as a checklist.

## Overview

Three release types exist in the v1.4 milestone:

- **Stable** — push or merge to `main` in each sub-repo triggers the existing pipeline
  (`release.yml` + `publish.yml` for the app; `build.yml` for the firmware). Auto-bumps
  the patch version. GitHub Release marked `make_latest: true`. Existing behavior —
  GATE-01 + GATE-02 from v1.4 preserve this verbatim.

- **Beta** — push to the `beta` branch OR `workflow_dispatch` on the new beta workflow in
  each sub-repo (`beta-release.yml` for the app; `beta-build.yml` for the firmware). Uses
  the explicit `BETA_VERSION` input to emit a PEP 440 pre-release identifier (`X.Y.ZbN` or
  `X.Y.ZrcN`). GitHub Release marked `prerelease: true`, `make_latest: false`.

- **Promotion (beta → stable)** — currently manual: fast-forward merge from `beta` to `main`
  after the beta is validated, followed by a normal stable release cut. Auto-promotion
  deferred to v1.5+ per REQUIREMENTS.md Future Requirements.

## Prerequisites

Before cutting a coordinated beta, confirm each item:

- `gh` CLI installed and authenticated with write access to both sub-repos:
  ```bash
  gh auth status
  gh api repos/henols/firestarter_app --jq '.permissions.push'   # must be true
  gh api repos/henols/firestarter --jq '.permissions.push'        # must be true
  ```

- Local clone of both sub-repos with their `beta` branches existing and up to date with the
  desired feature set (typically fast-forwarded from `main` or a feature branch).

- Operator has chosen the `BETA_VERSION` string per PEP 440: `X.Y.ZbN` (e.g. `3.1.0b1`,
  `3.1.0b2`) or `X.Y.ZrcN` (e.g. `3.1.0rc1`). See **Version string format** below.

- Phase 15 `update_version.py` extensions are present in both sub-repos (verify by running
  the two `BETA_VERSION_RE.pattern` snippets from `15-LOCKSTEP-PROCEDURE.md` §Prerequisites
  step 2).

## Version string format

Validation regex (identical in both `update_version.py` scripts, per VER-03):

```
^[0-9]+\.[0-9]+\.[0-9]+(b|rc)[0-9]+$
```

**Accepted:** `3.1.0b1`, `3.1.0b2`, `3.1.0rc1`, `0.0.1b1`, `1.2.3rc2`

**Rejected:**
- `3.1.0beta1` — pre-release label spelled out (use `b`, not `beta`)
- `3.1.0-b1` — separator before pre-release segment
- `3.1.0B1` — uppercase `B`
- `3.1.0a1` — alpha segment (out of scope for v1.4)
- `3.1.0` — no pre-release segment (this would be a stable version)
- `3.1.0.post1` — post-release segment (not supported)

**Monotonic increment rule:** The first beta on a base version line starts at `b1`
(e.g. `3.1.0b1`). Subsequent betas on the same base increment monotonically: `b2`, `b3`, etc.
Promotion from beta to release candidate requires an explicit operator decision — supply
`BETA_VERSION=X.Y.ZrcN` rather than relying on any automatic promotion.

**PyPI visibility:** PyPI stores pre-release versions normally. Consumers must pass
`pip install --pre firestarter==X.Y.ZbN` to opt in. Standard `pip install firestarter`
will NOT pull pre-release versions.

## Cutting a beta (lockstep)

Follow these steps in order. Each step is atomic; if any step fails, see **Failure recovery**
before re-running.

### Step 1 — Choose the lockstep version string

Select the `BETA_VERSION` to publish. Guidelines:
- For a v1.4 validation cut or Phase 19 E2E smoke test: use a clearly-test-only string
  such as `0.0.1b1` that cannot conflict with the current stable version lines
  (`2.0.7` for the app, `3.0.0` for the firmware).
- For a real beta cut: choose the next version base and append `b1`
  (e.g. `3.1.0b1` if the next planned stable release is `3.1.0`).
- Never reuse a `BETA_VERSION` that has already been published to PyPI or GitHub Releases
  without incrementing the beta counter — PyPI will reject duplicate uploads.

### Step 2 — Verify locally with the dry-run fixture

Run the lockstep fixture from the meta-repo root:

```bash
cd <meta-repo-root>
BETA_VERSION=<chosen-string> bash .planning/phases/15-versioning-locked-step-coordination-foundation/lockstep-dryrun-fixture.sh
```

Expected output (exit code 0):
```
LOCKSTEP DRY-RUN FIXTURE
========================
BETA_VERSION=<chosen-string>
App emits:       DRY_RUN: <chosen-string>
Firmware emits:  DRY_RUN: <chosen-string>

LOCKSTEP OK
```

If the fixture exits non-zero, do NOT proceed. Investigate the mismatch before triggering CI.

### Step 3 — (Optional) Desk-side dry-run per sub-repo

For additional confidence, run each script individually:

```bash
# App side (from firestarter_app/):
BETA_VERSION=<chosen-string> GITHUB_REF=refs/heads/beta \
  python3 .github/scripts/update_version.py --dry-run
# Expected: DRY_RUN: <chosen-string>

# Firmware side (from firestarter/):
BETA_VERSION=<chosen-string> GITHUB_REF=refs/heads/beta \
  python3 .github/scripts/update_version.py --dry-run
# Expected: DRY_RUN: <chosen-string>
```

Both must print `DRY_RUN: <chosen-string>` and exit 0.

### Step 4 — Trigger the app-side beta workflow

```bash
gh workflow run beta-release.yml \
  -R henols/firestarter_app \
  --ref beta \
  -f beta_version=<chosen-string>
```

Alternatively, use the GitHub web UI: Actions > Beta Release > Run workflow > fill in
`beta_version`.

Wait for the workflow to complete (`gh run watch` or refresh the Actions tab), then verify:
- The new GitHub Release in `firestarter_app` is marked **Pre-release** (not Latest).
- PyPI shows `<chosen-string>` on the `firestarter` project page.
- `pip install --pre firestarter==<chosen-string>` succeeds and
  `firestarter --version` reports `<chosen-string>`.

### Step 5 — Trigger the firmware-side beta workflow with the SAME `BETA_VERSION`

```bash
gh workflow run beta-build.yml \
  -R henols/firestarter \
  --ref beta \
  -f beta_version=<chosen-string>
```

Wait for the workflow to complete, then verify:
- The new GitHub Release in `firestarter` is marked **Pre-release** (not Latest).
- The release assets include the `firestarter_*.hex` build artifacts for each board target.
- The release body or `include/version.h` snapshot in the release contains
  `#define VERSION "<chosen-string>"`.

### Step 6 — Post-cut verification

Confirm all of the following before declaring the beta cut complete:

| Check | Command / Location | Expected |
|-------|--------------------|----------|
| App PyPI version | `pip show firestarter` or PyPI web | `<chosen-string>` |
| App CLI version | `pip install --pre firestarter==<chosen-string> && firestarter --version` | `<chosen-string>` |
| App GitHub Release tag | GitHub Release `firestarter_app/<chosen-string>` | Tagged, Pre-release=true |
| Firmware GitHub Release tag | GitHub Release `firestarter/<chosen-string>` | Tagged, Pre-release=true |
| Firmware version.h | In release assets or `firestarter` beta-branch HEAD | `#define VERSION "<chosen-string>"` |
| Both tags are string-equal | Compare the two release tag names | Byte-identical `<chosen-string>` |

## Verifying a beta (consumer-side smoke test)

On a fresh Python environment (clean venv or Docker container), run:

```bash
pip install --pre firestarter==<chosen-string>
firestarter --version                          # must print <chosen-string>
firestarter fw -i --pre                        # installs matching X.Y.ZbN firmware
firestarter fw -i --firmware-version <chosen-string>   # pins exact tag (alternative)
firestarter fw --list                          # enumerate; <chosen-string> appears in pre-release rows
```

Non-regression check — on a SEPARATE fresh stable install:

```bash
pip install firestarter                        # NO --pre flag → previous stable version
firestarter --version                          # X.Y.Z (no b/rc suffix)
firestarter fw -i                              # installs STABLE firmware, NOT <chosen-string>
```

Stable-installed app's bare `firestarter fw -i` must NOT pull the new beta — proves INST-01
non-regression.

## Promoting beta → stable (manual)

The promotion path is currently manual:

1. After the beta is validated (E2E + bench testing if applicable), fast-forward merge
   `beta` → `main` in each sub-repo:
   ```bash
   git checkout main && git merge --ff-only beta && git push origin main
   ```
2. The existing `main`-trigger pipeline (`release.yml` + `publish.yml` for the app;
   `build.yml` for the firmware) auto-bumps the patch version and produces a stable
   GitHub Release marked `make_latest: true`. GATE-01 + GATE-02 from v1.4 guarantee
   this stable-side behavior is byte-identical to pre-v1.4.
3. Delete the beta-tagged GitHub Release(s) if they are no longer needed (optional
   housekeeping; the stable release supersedes them functionally).

Auto-promotion workflow (e.g. a `promote.yml` that fast-forwards `beta` → `main` and bumps
to stable in one CI run) is deferred to v1.5+ per REQUIREMENTS.md "Future Requirements".

## Failure recovery

Lockstep is enforced at write time via the explicit `BETA_VERSION` input. If one workflow
fails after the other succeeded, apply the recovery below based on what failed:

| Scenario | Recovery action |
|----------|-----------------|
| App workflow failed before any file write or PyPI upload (e.g., CI test step failed) | Fix the failing test or build error; re-trigger the app workflow with the **same** `BETA_VERSION`. No drift — neither PyPI nor GitHub Release for the app exists yet. |
| App workflow succeeded and published to PyPI; firmware workflow failed at build or codegen gate | Fix the firmware issue; re-trigger the firmware workflow with the **same** `BETA_VERSION`. App is already published; firmware catches up to the same string. |
| App workflow created a PyPI release; same workflow re-triggered and PyPI rejects the upload with HTTP 400 "File already exists" | PyPI does not accept re-uploads of the same version. Increment `BETA_VERSION` to the next `bN` (e.g. `b2`) and run **both** workflows again with the new string to restore lockstep. This is a **known gap** per D-03; idempotent re-publish is deferred to a future milestone. |
| Firmware GitHub Release exists; app PyPI publish failed in the same attempted cut | Manually delete the firmware GitHub Release tag (from the Releases page or via `gh release delete <tag> -R henols/firestarter`), then re-cut both with the same `BETA_VERSION` from Step 4. Alternatively, increment `BETA_VERSION` and re-cut both. |
| Both workflows failed before any publish | Fix both issues; re-trigger both with the original `BETA_VERSION`. No published artifacts to undo. |

**v1.4-specific addendum:** When re-triggering after a partial failure, ALWAYS use the same
`BETA_VERSION` input value — never let `git-tag-scan` auto-resolve it on the retry (which would
emit `b1` or `bN+1` and silently desynchronize the two repos).

## Known gaps

- **Auto-promotion beta → stable workflow** — deferred to v1.5+; manual fast-forward merge is
  the only promotion path today.
- **Branch protection rules on the `beta` branch** — not configured; accidental force-pushes
  are possible. Deferred per REQUIREMENTS.md Future Requirements.
- **Signed release artifacts** (sigstore / GPG) — out of scope for v1.4; would cover both
  stable and beta in a dedicated milestone.
- **Idempotent beta re-publish on partial failure** — re-triggering with the same `BETA_VERSION`
  after a PyPI publish succeeded fails with PyPI HTTP 400 "File already exists"; recovery
  requires incrementing the beta counter and re-cutting both repos. Phase 15 D-03 known gap.
- **TestPyPI publishing channel** — rejected for v1.4 (PyPI `--pre` is the cleaner UX);
  could be revisited if beta operators report needing isolated install testing.
- **Cross-repo `repository_dispatch` automation** — rejected for v1.4 (requires cross-repo PAT
  with `repo` scope); manually-paired beta-branch push is the chosen mechanism.
