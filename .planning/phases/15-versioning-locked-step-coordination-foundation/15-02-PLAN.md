    def _git_tag_scan_fallback(base: str) -> str:
        try:
            result = subprocess.run(
                ["git", "tag", "--list", f"{base}b*"],
                capture_output=True, text=True, check=True
            )
            tags = result.stdout.strip().splitlines()
        except (subprocess.CalledProcessError, FileNotFoundError):
            tags = []
        n_re = re.compile(rf'^{re.escape(base)}b([0-9]+)$')
        nums = []
        for t in tags:
            m = n_re.match(t)
            if m:
                nums.append(int(m.group(1)))
        n = max(nums) + 1 if nums else 1
        return f"{base}b{n}"

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `BETA_VERSION` env var → file write | Untrusted string from `workflow_dispatch` input (operator-supplied) crosses into the version file. Must be regex-validated before file modification (ASVS V5). |
| `GITHUB_REF` env var → mode dispatch | GitHub-controlled value (`refs/heads/beta` vs `refs/heads/main`); equality check selects code path. Trust assumption: GitHub Actions correctly sets this; if subverted, stable path could be skipped. |
| Script stdout → `$GITHUB_OUTPUT` file | Phase 16's release workflow reads `steps.version.outputs.version` and uses it as the GitHub Release tag name. A malformed write could leak invalid tag names into a public release. |
| `git tag --list` subprocess output → version computation | Git tags in the repo are read and parsed for the fallback path. Tags can be created by anyone with push access; a maliciously-named tag could influence the next version number. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-02-01 | Tampering / Injection | `BETA_VERSION` env var → `__init__.py` write | mitigate | `BETA_VERSION_RE = ^[0-9]+\.[0-9]+\.[0-9]+(b|rc)[0-9]+$` validates BEFORE file open (D-21). Regex allows only digits, `.`, `b`, `rc` — no path traversal characters, no shell metacharacters, no newlines. ValueError raised pre-write. Asserted by `test_beta_invalid_version_rejected`. |
| T-15-02-02 | Tampering | Operator error supplying a `BETA_VERSION` that collides with an existing stable version (e.g. `BETA_VERSION=2.0.7` — missing `b1` suffix → fails regex → script aborts) | mitigate | The D-21 regex REQUIRES a `(b|rc)N` suffix, so a bare stable-shaped version is rejected; operator cannot accidentally publish a beta with a stable-shaped tag that would clash with PyPI. |
| T-15-02-03 | Spoofing | Malicious git tag (e.g., `1.2.3b99999999999999999999`) influencing fallback | accept | Fallback path is operator-controlled (only invoked when `BETA_VERSION` unset on a beta-branch push); D-08 fallback intentionally trusts the local repo's tag namespace. Mitigation: Phase 18 procedure documents that operators should use explicit `BETA_VERSION` for production cuts (D-01) — fallback is for local dev. Acceptable risk given the threat actor would need push access to create the tag. |
| T-15-02-04 | Information Disclosure | `subprocess.run(["git", "tag", "--list", ...])` could leak repo tags to logs | accept | Tag names in this repo are not secrets; CI logs already expose tag names through the release workflow. No PII or credentials in tag namespace. |
| T-15-02-05 | Denial of Service | Stable path broken by `get_version()` return-signature change (RESEARCH Pitfall 4) | mitigate | Single caller (`calculate_version()`) is updated in lockstep to unpack 4-tuple (`major, minor, patch, _pre = ...`). | T-15-02-06 | Elevation of Privilege | `BETA_VERSION` set on a non-beta branch could enter beta mode unintentionally | accept | Per D-06 (intentional design), `BETA_VERSION` presence forces beta mode even when `GITHUB_REF != refs/heads/beta` — supports CI/test invocation. This is a documented feature, not a bug. Phase 18 procedure must clarify operator responsibility. |
