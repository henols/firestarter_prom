## Summary

Phase 67.1 closes the two outstanding v1.12 database gaps identified by the milestone audit: DB-02 (pinout classification for currently-misclassified DIP chips) and DB-04 (operator-facing status-specific capability reporting). All work is HOST-ONLY in `firestarter_app/`; no firmware changes.

**DB-02 key finding (VERIFIED):** The current `chip_database.json` has 0 chips with `pinout: null`. The milestone audit's phrase "unclassifiable" refers to chips that reach the wrong pinout via silent fallback in `resolve_pinout_key` — not a hard None. There are exactly **14 chips in 2 groups** that currently receive incorrect pinouts due to fallback-path gaps:
- 4 × 24-pin SRAM (DS1220(RW), FM1208, M48T02/12, ST/M48T02/12): get `DIP24_2716` (EPROM pinout, wrong) instead of `DIP24_6116` (SRAM pinout with `rw-pin=21/WE`).
- 10 × 28-pin native-SRAM (6264, 62256, W2464, W24256, DS1225(TEST), DS1230(TEST), BQ401x(TEST)): get `DIP28_2764` (EPROM pinout, wrong) instead of `DIP28_JEDEC_SRAM_8K` (8K variants) or `DIP28_28C256` (32K variants with A14 at pin 1).

These chips have `support_status: supported` today but would fail hardware write because their bus-config is wrong (no `rw-pin`/WE in bus-config; wrong VPP assertion).

**DB-04 key finding (VERIFIED):** Approximately 70% is already delivered (66-05 refusal guard + Phase 69 display robustness). The remaining delta is:
- SC#1: `firestarter info <non-supported-chip>` currently shows NO support-status line. The `raw_config` already contains `support_status` and `unsupported_reason` fields but these are never passed to the display layer.
- SC#2: Chip-op refusal message prefix is generic ("Chip not usable:") rather than per-status formatted ("VPP Xv exceeds programmer max" / "adapter required: …" / "protocol not implemented").
- SC#4: Existing tests assert only "no crash" and chip name presence; a per-status CLI matrix asserting the status-specific text does not exist.

**Primary recommendation:** One combined phase with two workstreams: (A) DB-02 SRAM pinout repair in `build_db.py` + DB regen + gate verification, and (B) DB-04 status-specific narrative in info display + chip-op refusal + per-status CLI test matrix.

## DB-02: Unclassifiable Chip Enumeration

### Group 1: 24-pin SRAM — 4 chips (VERIFIED via live infoic.xml)

All 4 chips have `pm_idx=0`, upstream `proto=0x0B` (EPROM_LEGACY), `type=4` (SRAM), `variant_lo=16`.

| Chip | Mfg | Algorithm after override | Current pinout | Correct pinout |
|------|-----|--------------------------|----------------|----------------|
| DS1220(RW) | DALLAS | 0x28 | DIP24_2716 (wrong) | DIP24_6116 |
| FM1208 | RAMTRON | 0x28 | DIP24_2716 (wrong) | DIP24_6116 |
| M48T02, M48T12, M48Z02, M48Z12 | SGS-THOMSON | 0x28 | DIP24_2716 (wrong) | DIP24_6116 |
| M48T02, M48T12 | ST | 0x28 | DIP24_2716 (wrong) | DIP24_6116 |

**Root cause (VERIFIED):** The fm1608 override block (`build_db.py:518-537`) sets `pinout_key` directly for 28-pin chips but has NO 24-pin branch. For 24-pin, `pinout_key` was already set at line 445 by `resolve_pinout_key(24, variant=0x4310, flags, pm_idx=0, proto_id=0x0B)`:
- Tier 1: `(24, 0, 0x0B)` not in `PIN_MAP_PROTO_TO_PINOUT` → miss
- Tier 2: `(24, 0)` → `None` in `PIN_MAP_TO_PINOUT` → fall through
- Tier 3: `variant_lo=16` (not 1) → `DIP24_2716`

**Fix (VERIFIED):** Add a 24-pin branch inside the fm1608 override block:
```python
if type_int == 4 and proto_id in (0x07, 0x08, 0x0B):
    proto_id = 0x28
    if pin_count == 28:
        if mem_size <= 8192:
            pinout_key = "DIP28_JEDEC_SRAM_8K"
        else:
            pinout_key = "DIP28_28C256"
    elif pin_count == 24:            # ADD THIS BRANCH
        pinout_key = "DIP24_6116"    # 24-pin SRAM: WE on pin 21
```

**Evidence:** `DIP24_2716` has `vpp-pin=[21]`; `DIP24_6116` has `rw-pin=[21]` (WE). DS1220 datasheet: pin 21 = WE (write enable). The `DIP24_6116` entry comment cites `piersfinlayson/one-rom` datasheet-verification. [VERIFIED: live infoic.xml + pinouts.json inspection]

**Safety note:** No VPP hazard — `configure_sram` never asserts VPP regardless of pinout. The functional issue is that SRAM write fails silently (no `rw-pin` in bus-config = no WE strobe).

### Group 2: 28-pin native SRAM — 10 chips (VERIFIED via live infoic.xml)

All chips have `pm_idx=0`, native `proto=0x28` (SRAM_STD), `type=4` (SRAM). The fm1608 override does NOT fire for these (it only triggers on proto `0x07/0x08/0x0B`).

| Chip | Mfg | Size | variant_lo | Current pinout | Correct pinout |
|------|-----|------|-----------|----------------|----------------|
| DS1225(TEST) | DALLAS | 8K | 0 | DIP28_2764 (wrong) | DIP28_JEDEC_SRAM_8K |
| DS1230AB(TEST), DS1230Y(TEST) | DALLAS | 32K | 2 | DIP28_2764 (wrong) | DIP28_28C256 |
| DS1230W(TEST3.3V) | DALLAS | 32K | 2 | DIP28_2764 (wrong) | DIP28_28C256 |
| BQ4010YMA(TEST) | TI | 8K | 0 | DIP28_2764 (wrong) | DIP28_JEDEC_SRAM_8K |
| BQ4011YMA(TEST), BQ4011LYMA(TEST3.3V) | TI | 32K | 2 | DIP28_2764 (wrong) | DIP28_28C256 |
| W2464, W2465 | WINBOND | 8K | 0 | DIP28_2764 (wrong) | DIP28_JEDEC_SRAM_8K |
| W24256, W24257A | WINBOND | 32K | 2 | DIP28_2764 (wrong) | DIP28_28C256 |
| 6164, 6264 | Standard SRAM | 8K | 0 | DIP28_2764 (wrong) | DIP28_JEDEC_SRAM_8K |
| 61256, 62256 | Standard SRAM | 32K | 2 | DIP28_2764 (wrong) | DIP28_28C256 |

**Root cause (VERIFIED):** `resolve_pinout_key(28, variant_lo=0_or_2, flags, pm_idx=0, proto_id=0x28)`:
- Tier 1: `(28, 0, 0x28)` not in `PIN_MAP_PROTO_TO_PINOUT` → miss
- Tier 2: `(28, 0)` → `None` → fall through
- Tier 3: `DIP28_VARIANT_MAP.get(0, "DIP28_2764")` = `"DIP28_2764"` (wrong)

**Fix:** Add entries to `PIN_MAP_PROTO_TO_PINOUT`. The size discrimination (`mem_size`) is NOT available as a parameter in `resolve_pinout_key` — the function signature is `(pin_count, variant, flags_int, pm_idx=None, proto_id=None)`. Two implementation approaches:

*Option A — Add mem_size parameter to resolve_pinout_key:*
```python
def resolve_pinout_key(pin_count, variant, flags_int, pm_idx=None, proto_id=None, mem_size=None):
    ...
    # New rule for native 28-pin SRAM:
    if pin_count == 28 and pm_idx == 0 and proto_id == 0x28:
        if mem_size is not None and mem_size > 8192:
            return "DIP28_28C256"   # 32K SRAM: A14 at pin 1, 15 addr bits
        return "DIP28_JEDEC_SRAM_8K"  # 8K SRAM: 13 addr bits
```

*Option B — Handle in build_db.py alongside fm1608 block:*
Add an adjacent block after the fm1608 override that handles native `proto=0x28 type=4` chips similarly, setting `pinout_key` directly using `mem_size`.

Option B is lower-risk (less interface change). The planner should decide.

**Evidence:** `DIP28_JEDEC_SRAM_8K` comment confirms "same address bus as DIP28_2764 (A0-A12, 13 address bits for 8K)" [VERIFIED: pinouts.json]. `DIP28_28C256` has 15 address bits + `rw-pin=27` [VERIFIED: pinouts.json]. JEDEC 62256 standard pinout: A14 at pin 1, WE at pin 27 — matches `DIP28_28C256` layout [ASSUMED from JEDEC SRAM standard, confirmed by minipro chip family clustering].

## Common Pitfalls

### Pitfall 1: Adding (28, 0, 0x28) rule without mem_size discriminator
**What goes wrong:** All 28-pin native SRAM (both 8K and 32K) route to `DIP28_JEDEC_SRAM_8K` (only 13 address bits). 32K SRAM (62256, W24256, DS1230) need `DIP28_28C256` (15 address bits).
**Root cause:** `resolve_pinout_key` does not currently receive `mem_size`. Adding a flat `(28, 0, 0x28) → DIP28_JEDEC_SRAM_8K` rule misclassifies 32K chips.
**How to avoid:** Either add `mem_size` parameter to `resolve_pinout_key` and add discriminated rules, OR handle this case in the `main()` loop directly (like the fm1608 block does for 28-pin).
**Warning signs:** `diff_db.py` shows 62256/W24256/DS1230 pinout = `DIP28_JEDEC_SRAM_8K` — that's wrong for 32K.

### Pitfall 2: DB-02 changes triggering test_list snapshot failure
**What goes wrong:** `test_characterization.py::test_list` snapshot captures the full list output. If any displayed field changes, the snapshot fails.
**Root cause:** The list table shows Name, Manufacturer, Pins, Type, VPP — NOT pinout. Type for corrected SRAM chips should stay "SRAM" (no change). VPP for SRAM is "-" (no VPP). So snapshot should be stable.
**How to avoid:** Run `pytest tests/test_characterization.py::test_list` specifically after DB regen to confirm.
**Warning signs:** Snapshot diff showing SRAM chip lines changing in the Type or VPP columns.

### Pitfall 3: DB-04 info display changes triggering test_info_known_chip snapshot failure
**What goes wrong:** The snapshot for `test_info_known_chip` (W27C512) fails because a new "Support status" line was added even for supported chips.
**Root cause:** If the status display block renders unconditionally.
**How to avoid:** Gate the status display block on `support_status != "supported"` — supported chips get no new line.
**Warning signs:** Snapshot diff showing a new "Support status: supported" line.

### Pitfall 4: 3.12-masks-3.11 ruff drift in build_db.py
**What goes wrong:** New code in `build_db.py` uses Python 3.12 syntax (f-string backslashes, etc.) that passes ruff locally but fails CI (3.11).
**Root cause:** The devcontainer runs Python 3.12 which accepts syntax Python 3.11 rejects.
**How to avoid:** `build_db.py` is in `tools/` — NOT checked by `ruff check firestarter/ tests/`. But if new code in `firestarter/*.py` files uses 3.12 syntax, CI would catch it. Follow the same rule: avoid f-string backslashes and 3.12-specific syntax in any production code.
**Warning signs:** CI fails with `SyntaxError` or ruff parse error on the 3.11 runner.

### Pitfall 5: `ChipNotImplementedError` in `chip_resolver.py` — strict mypy
**What goes wrong:** If `support_status` is added as a typed field on `ChipNotImplementedError` (Approach B), the constructor signature change must be type-annotated correctly.
**Root cause:** `chip_resolver.py` and `exceptions.py` are in the strict mypy set.
**How to avoid:** Any changes to `exceptions.py` or `chip_resolver.py` must pass `python tools/check_mypy_watermark.py`. Current watermark is 29.
**Warning signs:** Watermark check reports > 29 errors.

### Pitfall 6: fm1608 override ordering — resolve_pinout_key is called BEFORE fm1608 block
**What goes wrong:** A developer adds a rule to `PIN_MAP_PROTO_TO_PINOUT` for `(24, 0, 0x0B)` thinking it will override for DS1220/FM1208, but `resolve_pinout_key` is called at line 445 with the ORIGINAL `proto_id=0x0B` before the fm1608 override changes it to 0x28. This would work for the pinout lookup but not for the algorithm dispatch.
**Root cause:** Line 445 `pinout_key = resolve_pinout_key(...)` is called before the fm1608 block at line 518.
**How to avoid:** For 24-pin fm1608 chips, add the fix INSIDE the fm1608 override block (lines 518-537), setting `pinout_key` directly — same pattern as the existing 28-pin branch. Do NOT add `(24, 0, 0x0B)` to `PIN_MAP_PROTO_TO_PINOUT` as a shortcut (the proto_id at call time is 0x0B, but the correct pinout is the SRAM one which belongs with the override context).
**Warning signs:** DS1220(RW) gets `DIP24_6116` but algorithm stays 0x0B instead of 0x28.
