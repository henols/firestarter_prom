<objective>
Close the SC#3 / DB-05 BLOCKER that survived 66-04 (confirmed in 66-VERIFICATION.md
and 66-REVIEW.md CR-01). 66-04 demoted `algorithm` to `0x00` for all 14 non-supported
chips and proved `dispatch(0, None)=ERROR` in a SIMULATION — but the simulation does
not match the real host path. `database.py::_map_data` ignores `support_status` entirely;
when `algorithm==0` (falsy) it falls to an `electrical.type` string heuristic, so the 4
`vpp-exceeds-max` UV-EPROM entries (INTEL/M2716,M2716M · INTEL/2732,2732A,M2732,M2732A ·
SGS-THOMSON/ETC2716,M2716 · ST/ETC2716,M2716) emit a wire dict `{algorithm:0, type:1}`.
Firmware `configure_memory` routes `protocol==0` + `mem_type==1 (TYPE_EPROM)` to
`configure_eprom`, which engages the 12V VPP boost regulator — a hardware-damage path.
The 9 `adapter-required` 24-pin EEPROMs are only INCIDENTALLY safe (etype="Flash/EEPROM"
-> mem_type=2 -> no firmware handler); safety must NOT depend on that string.

Per operator decision D-12 (CONTEXT.md — supersedes the D-10 "host refuses at Phase 68"
fence for the host guard only), this gap-closure pulls the Phase 68 (DB-04) host-refusal
guard forward and delivers BOTH halves of the verifier's structured remediation:

- Option A: an authoritative runtime host guard (`chip_resolver.resolve_chip` raises
  `ChipNotImplementedError` before any program-capable wire dict is built) — closes the
  actual hazard.
- Option B: realign `check_dispatch.py` + the 8th CI test to model `_map_data`'s real
  mem_type derivation AND the new host-guard exemption — so the gate stays GREEN AND
  TRUTHFUL, and FAILs on any FUTURE reintroduction (e.g. a non-supported chip that both
  derives a real handler AND is not refused by the host guard).

Purpose: a `firestarter write M2716` (or read/erase/verify) must be refused on the host
before any serial byte is sent, driven by `support_status`, not by the etype string.
Output: the host guard, its wiring, a runtime-boundary test, and a gate/CI realignment.

HOST-ONLY — only the `firestarter_app/` sub-repo. No firmware change. No DB regeneration
(this is runtime code, not DB data — `chip_database.json` must NOT churn; if it does, that
is a red flag to surface).
</objective>
