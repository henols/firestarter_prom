### ERR-01 — BUG-2 fix shape (locked per scout — directional from xfail text)
- **D-01:** **Split the conflated except clause into two clauses with corrected log labels.** Today's `eprom_operations.py:265` reads `except (SerialError, SerialTimeoutError, EpromOperationError) as e: logger.error(f"Communication error during {op}: {e}")` (the xfail assertion in `test_bug_characterization.py:118-126` explicitly asserts "EpromOperationError must NOT be logged as 'Communication error'").  
  ```python
  except (SerialError, SerialTimeoutError) as e:
      logger.error(f"Communication error during {operation_name}: {e}")
      return False, str(e)
  except EpromOperationError as e:
      logger.error(f"Programmer error during {operation_name}: {e}")
      return False, str(e)
  ```
  Reasoning: minimum diff that satisfies the xfail assertion. The "Programmer error" wording matches the existing convention used elsewhere (`firestarter_app/firestarter/eprom_operations.py:265-275` docstring already describes the load-bearing semantic). Behavior preserved: both clauses return `(False, str(e))` identically; the only user-visible change is the log label, which is NOT pinned by any snapshot (the snapshots pin CLI output, not log output). Phase 41's BUG-1 fix pattern (single atomic Wave commit) is mirrored.
- **D-02:** **Flip the xfail in Wave 1.** Delete the `@pytest.mark.xfail(strict=True, reason="BUG: eprom_operations.py:265 conflates EpromOperationError with SerialError; fix lands Phase 42 (ERR-01)")` marker block at `test_bug_characterization.py:74-80`; the test's assertion body already encodes the corrected behavior (it asserts the `EpromOperationError` log does NOT contain "Communication error"). ### ERR-01 — Click-boundary mapping mechanism (locked per Phase 41 D-09 + scout)
- **D-03:** **Centralized `@map_typed_errors` decorator on every Click handler in `cli_handlers.py`.** Replace the `_resolve_or_exit(name, db) -> Optional[dict]` shim (`cli_handlers.py:98-113`) and the per-handler `sys.exit(0 if op() else 1)` bool-to-int pattern with a single decorator that:
  ```python
  def map_typed_errors(f):
      """Map service-layer typed exceptions to ClickException + stable exit codes."""
      @functools.wraps(f)
      def wrapper(*args, **kwargs):
          try:
              return f(*args, **kwargs)
          except ChipNotFoundError as e:
              raise click.ClickException(str(e)) from e   # exit 1
          except FirmwareOutdatedError as e:
              raise click.ClickException(f"Firmware outdated: {e}") from e   # exit 1
          except (SerialError, SerialTimeoutError) as e:
              raise click.ClickException(f"Communication error: {e}") from e   # exit 1
          except EpromOperationError as e:
              raise click.ClickException(f"Programmer error: {e}") from e   # exit 1
          except HardwareOperationError as e:
              raise click.ClickException(f"Hardware error: {e}") from e   # exit 1
      return wrapper
  ```
  Applied to every `@cli.command()` and `@cli.group()` callback. `click.ClickException` prints to stderr and exits 1 by default — matches today's behavior for these error types. Chip-op handlers stop calling `_resolve_or_exit` and instead call `resolve_chip(name, db=app.db)` directly; the decorator catches `ChipNotFoundError` uniformly. The `sys.exit(0 if op() else 1)` bool-to-int pattern stays for the bool-returning service methods (`eprom_operator.write_eprom() -> bool` etc.) — but typed exceptions raised from inside those calls bubble up to the decorator. Click's automatic `UsageError` / `BadParameter` (exit 2) handling stays unchanged.
- **D-04:** **Keep all exception-driven exits at code 1 — do NOT introduce a distinct exit code for `EpromOperationError`.** Rationale: GATE-1.8b explicitly preserves end-user exit codes; introducing exit 3 for "programmer error" would (a) require updating all of Phase 36's CLI characterization snapshots AND Phase 41's `test_cli_handlers.py` `assert result.exit_code == 1` assertions (verified — exit codes 0/1 pinned across ~30+ assertions in `test_cli_handlers.py` + 29 syrupy snapshots in `test_characterization.ambr`); (b) qualify as an INTENTIONAL BEHAVIOR CHANGE that's a *feature* (UX richness), not a *bug fix* — violates the v1.8 "refactor + fix bugs found" gate; (c) is uninformative to end users without documentation (no shell script today expects exit 3). The "stable exit codes (0 success, 1 expected failure, 2 usage error)" wording in ERR-01 SC#1 is about *consistency* around the existing three codes, not introducing a new one. Defer richer exit-code semantics to a future milestone if real demand surfaces.
- **D-05:** **Delete `_resolve_or_exit` once `map_typed_errors` is applied to all 9 chip-op handlers + `dev read` / `dev addr`.** The 9 sites at `cli_handlers.py:380, 458, 481, 504, 524, 553, 738, 974, 1043` (approximate; planner will enumerate exact lines) currently call `_resolve_or_exit` followed by `if not eprom_data: sys.exit(1)`. Replace with a direct `resolve_chip(eprom, db=app.db)` call (raises `ChipNotFoundError` → decorator catches → `ClickException` → exit 1). Phase 41 D-08 explicitly seeded this as the load-bearing intent ("Phase 42 ERR-01 will replace `_resolve_or_exit` with `raise ClickException` flowing from `chip_resolver.resolve_chip` directly"). The shim is removed cleanly; no half-decorator.
