<objective>
Close audit-gap WARNING-2 (REQ-SAF-02 forward-compat for AT28C 5V EEPROM) by adding an A9-12V hardware chip-identification check to `eeprom28c_write_init`, gated on `handle->chip_id > 0`, running BEFORE the SDP-disable sequence. Cover SAF-06's chip-id half with four Unity tests on `[env:native]` (matching / mismatching / zero-skip / FORCE) in a brand-new suite-local test directory so the shared dispatch suite stays byte-identical.

**Decision override (load-bearing):** CONTEXT.md D-05 prescribed the AMD/SST software JEDEC sequence (`AA→0x5555, 55→0x2AAA, 90→0x5555`). The phase researcher disproved this on datasheet grounds: the AT28C family identifies via A9 raised to 12V reading the upper 64 bytes (0x7FC0..0x7FFF on AT28C256, 0x1FC0..0x1FFF on AT28C64). This plan implements RESEARCH.md "Option A" — mirror `eprom_get_chip_id` (the existing UV-EPROM A9-12V path). CONTEXT.md D-05 is overridden by RESEARCH.md per the discovery-evidence-supersedes-assumption convention; this is recorded in `must_haves.truths` for downstream auditors.

Purpose: Make REQ-SAF-02 hold the moment any algorithm=0x0D entry gains a non-zero `chip_id_value` (forward-compat — no DB chip triggers it today, but the firmware path must be ready). Init-time fail-fast: mismatching identity errors and aborts BEFORE the SDP-disable state mutation, so a wrong chip in the socket stays write-protected.

Output:
- One new static helper `eeprom28c_check_chip_id` in `firestarter/src/proms/eeprom_28c.cpp` (no header change).
- One insertion in `eeprom28c_write_init` (gate + call + early-return — 5 lines).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| chip → firmware (data bus during A9-12V mode) | The bytes read from the AT28C upper 64-byte identification region cross into the firmware as `handle->firestarter_get_data(handle, mem_size - 64)` and `... - 63`. These bytes are user-writable on the AT28C family (per Microchip AT28C64B datasheet §6.7); the firmware treats them as the authoritative identity claim — but the operator authored them at programming time, so they are trustworthy in the sense the operator chose to write them and expects them on read-back. |
| socket (wrong chip inserted) | An operator inserting an unintended chip in the socket and triggering a write would, without this plan, get SDP-disable + page-write — possibly bricking the chip if its addressing is different. With this plan, identity is checked first; mismatch errors and aborts before any state mutation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Spoofing (operator/socket) | An unintended chip inserted in the socket gets identified as the expected chip and writes proceed. | mitigate | This plan's `eeprom28c_check_chip_id` reads the AT28C identification region under A9-12V mode and compares against `handle->chip_id`. Mismatch sets `response_code = RESPONSE_CODE_ERROR` (or `WARNING` with `FLAG_FORCE`); caller early-returns BEFORE `flash_execute_command(EEPROM_SDP_DISABLE)`, so the chip stays in its protected state. Forward-compat: today no algorithm=0x0D entry sets `chip_id_value`, but the moment one does (DB override or future upstream change) the check fires. |
| T-01-05 | Tampering | The new helper toggles `REGULATOR` and `A9_VPP_ENABLE` and then clears both. A bug here that left A9_VPP_ENABLE asserted would route 12V to A9 during the subsequent SDP-disable / page-write — silent chip damage. | mitigate | The helper mirrors `eprom_get_chip_id` byte-for-byte for the regulator sequencing (assert REGULATOR, delay 50, assert A9_VPP_ENABLE, delay 100, read, clear both via the single `set_control_register(REGULATOR \| A9_VPP_ENABLE, 0)` call). This sequencing is v1.0-verified on W27C512 hardware. The 4 native tests assert on `response_code`; the register sequencing has no native test but is byte-identical to the verified analog. |
| T-01-06 | Denial of service (regression) | The new gate could spuriously block writes on chips where the identification bytes happen to be 0xFFFF (factory-erased). | accept | The gate is `if (handle->chip_id > 0)` — `chip_id == 0` means "no expected ID, skip the check entirely". So factory-erased chips that the DB does not configure with `chip_id_value` are unaffected. If a user populates `chip_id_value = 0xFFFF`, that is their choice and the check correctly compares against it. |

Severity: low — firmware regression risk and forward-compat scaffolding; no external attack surface. Block-on threshold per project config = high; this plan is well below the block-on threshold.
