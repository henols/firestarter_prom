DB override mechanism (RESEARCH.md-corrected D-05; live-grep verified):
- File path: `~/.firestarter/database.json` (from `firestarter_app/firestarter/config.py:16,19` — `DATABASE_FILE = os.path.join(os.path.expanduser("~"), ".firestarter", "database.json")`).
- Merge function: `firestarter_app/firestarter/database.py:213-238` `_merge_databases`. Schema-of-merge:
  - Iterates `manual_db.items()` (override) — top-level keys are MANUFACTURER strings.
  - For each existing manufacturer key in base DB, builds `existing_names = {item["part_number"]: item for item in db[key]}` (NOTE: keyed by `part_number` in the base DB).
  - For each override item, looks up `manual_item.get("name")` against the existing_names dict.
  - On match: `existing_names[manual_item["name"]].update(manual_item)` — **shallow** dict.update overlay (the override item's keys overwrite the base item's keys).
- **Critical:** the override uses key `"name"` (NOT `part_number`); the lookup matches `manual_item["name"]` against the base item's `"part_number"`. The override skeleton must use `"name": "AM28F010"`.
- Note on shallow-merge: a shallow `.update()` on the top-level chip dict means setting `vpp_mv` directly at the top level of the override item DOES NOT modify the nested `electrical.vpp_mv` field. The wire emit at `database.py:_map_data` reads `electrical.get("vpp_mv", 0)` (per RESEARCH.md §"Phase 01" cite). For the override to actually flip the wire `vpp_mv`, the override item's `electrical` sub-dict must replace the base item's `electrical` sub-dict (since shallow update replaces top-level `electrical` wholesale).
- **Therefore the override file must carry the FULL `electrical` sub-object** (size_bytes, type, pin_count, vpp, vdd, vcc) with only `vpp_mv` flipped to 8000. Same for `programming` — leave intact (algorithm, pulse_duration, chip_id_check, chip_id_value preserved as-is in the override, OR omit and let shallow-merge preserve them).

- The full chip spec stub MAY also include `programming` (algorithm/pulse_duration/chip_id_check/chip_id_value) for completeness — but if omitted, shallow-merge preserves the base entry's `programming` block intact. Either form is acceptable; the override skeleton above is the minimum required to flip `vpp_mv` to 8000.

Pitfalls relevant to this plan (per RESEARCH.md):
- **Pitfall #1 — VPP-LOW branch trap.** Lowering the regulator (not the DB setpoint) would route through the WARN branch and the write would proceed. The DB override above is the correct mechanism — lower `handle->vpp_mv` while leaving the regulator at ~12 V.
- **Pitfall #5 — FLAG_FORCE trap.** `firestarter write -f` downgrades VPP-HIGH ERROR to WARNING. Sub-run A invocation MUST NOT carry `-f` or `--force`. Document this constraint in §5 Sub-run A.
- **Pitfall #6 — Chip-ID mismatch on AM28F010.** If Sub-run B's nominal write reports `ERROR: Chip ID 0xXXXX dont match expected ID 0x01a7`, the chip is a re-mark or different stepping. Per D-07, classify as chip-specific issue; SAF-04 closure is separately validated by Sub-run A so the abort gate is already proven. Document `-f` use IF and ONLY IF Sub-run B's chip-ID error is suppressed for the nominal-write-only purpose — but this means the chip-ID separate concern is documented, not that SAF-04 was bypassed.
- **Pitfall #4 — Operator-error categories.** Forgetting to remove the override before Sub-run B is the most likely operator error; it would cause Sub-run B to also abort with the same VPP-HIGH error. Retry; do NOT log as FAIL.
- **Pitfall #3 (cross-borrowed from HW-04)** — N/A here (AM28F010 has no SDP-disable issue).
