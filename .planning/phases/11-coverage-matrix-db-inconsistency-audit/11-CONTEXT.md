# Phase 11: Coverage Matrix & DB Inconsistency Audit - Context

**Gathered:** 2026-05-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 11 produces **one** desk-side artifact — `.planning/v1.3-COVERAGE-MATRIX.md` — and **fixes** the DB count drift that this audit surfaces in the planning docs.

The matrix is a single self-contained markdown file with five sections (in order):

1. **Summary stats** — total chip count, per-algorithm counts, per-pinout-class counts, per-size-bucket counts, per-pulse-bucket counts.
2. **DB Count Reconciliation** — call out where ROADMAP.md (214 algo-0x07 + 127 algo-0x08 = 341 chips), REQUIREMENTS.md (same 341), and PROJECT.md (743 total chips) diverge from the live DB (734 total, 212 algo-0x07, 127 algo-0x08). Phase 11 fixes those numbers in the planning docs as part of the plan.
3. **Full Enumeration** — every algo-0x07 + algo-0x08 row in `chip_database.json`. Group by **algorithm → pinout class → size_bytes ascending → manufacturer alpha**. Columns: manufacturer, part_number(s), pin_count, size_bytes, pulse_duration, chip_id_check, chip_id_value, pinout, electrical.type.
4. **DB Inconsistencies / Defect Candidates** — each finding flagged with severity tier + stable ID + metadata (see `<decisions>` below).
5. **BENCH Coverage Proof** — three per-axis coverage tables (pinout-class / pulse-duration bucket / size bucket) demonstrating BENCH-01..06 represent the family; uncovered cells called out explicitly.

The matrix is generated by a **committed Python tool**, `firestarter_app/tools/audit_coverage_matrix.py`, that mirrors `tools/check_dispatch.py` (same `EpromDatabase` loader, same `_ALGO_MEM_TYPE` reuse, same exit-code discipline). It is re-runnable when `chip_database.json` is regenerated from `infoic.xml`.

**In scope:**
- New tool `firestarter_app/tools/audit_coverage_matrix.py` (committed, idempotent generator).
- Output file `.planning/v1.3-COVERAGE-MATRIX.md` (single combined file).
- Targeted edits to `.planning/PROJECT.md`, `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md` to fix the 734 / 743 + 212 / 214 / 341 drift.

**NOT in scope:**
- Auto-fixes against `chip_database.json` or `tools/build_db.py` — defect candidates are documented only, never patched in v1.3. Fixes route to v1.4 or sub-repo PRs.
- Bench-level validation of any chip (Phase 12 / Phase 13).
- BENCH-05 / BENCH-06 chip selection — Phase 11 flags uncovered pinouts; Phase 12 CONTEXT.md owns the selection decision.
- BENCH-RESULTS.md / milestone close paperwork (Phase 14).
- Any change to firmware or to `firestarter_app` runtime code (the new tool sits under `tools/` like `check_dispatch.py` / `build_db.py` and is not part of the installed pip package).

<decisions>
## Implementation Decisions

### Generator artifact

- **D-01: Committed Python tool.** New `firestarter_app/tools/audit_coverage_matrix.py`. Mirrors the style of `firestarter_app/tools/check_dispatch.py` — module-top `_DATA_DIR` / `DB_FILE` constants with the same `FIRESTARTER_DB_FILE` env-var escape hatch; imports `from firestarter.database import EpromDatabase`; iterates the DB the same way. Re-runnable when `chip_database.json` regenerates from `infoic.xml`.
- **D-02: Idempotence required.** Same DB input → byte-identical matrix output. Stable sort keys: (algorithm asc, pinout-class asc lexicographic, size_bytes asc, manufacturer asc, first part_number variant asc). No timestamps in output. Mirrors the codegen idempotence rule already established in Phase 06 Plan 06-01 (`[[feedback_always-mirror-uno-leonardo-tests]]` is a different rule — the relevant precedent is "codegen idempotence by sort + LF + no timestamp").
- **D-03: Exit-code discipline.** `0` = matrix generated cleanly, no NEW defect candidates appeared since the last committed matrix. `1` = at least one new defect candidate or a fatal DB-parse error. This lets the same tool be wired as a CI drift gate later (mirrors `check_dispatch.py` exit codes; not wired to CI in Phase 11 — out of scope, just keep the door open).
- **D-04: Output path is hardcoded but overridable.** Default writes to `.planning/v1.3-COVERAGE-MATRIX.md` from project root. `--output PATH` flag allows redirection for dry-run / tmp comparison. Mirrors `build_db.py` CLI style.

### Output structure + DB-count reconciliation

- **D-05: Single combined file** at `.planning/v1.3-COVERAGE-MATRIX.md`. No companion files. Section order is fixed: Summary stats → DB Count Reconciliation → Full Enumeration → DB Inconsistencies / Defect Candidates → BENCH Coverage Proof. Operator scrolls once to triage; v1.4 backlog grooming reads §4 standalone.
- **D-06: Grouping inside the Full Enumeration table.** Algorithm (0x07 first, 0x08 second) → pinout class (lexicographic asc: DIP28_27256 → DIP28_27512 → DIP28_2764 → DIP28_28C256 → DIP28_28C64 → DIP32_STD) → size_bytes asc → manufacturer alpha asc. Within a manufacturer the row covers the entire `part_number` comma-joined variant set (e.g. one row for `W27C512,W27E512` not two). The matrix records the variant string verbatim; "row count" and "variant count" both surface in summary stats.
- **D-07: Phase 11 also reconciles planning-doc drift.** Live DB: 734 chips total, 212 algo-0x07, 127 algo-0x08, 339 in-scope-for-v1.3 (not 743 / 214 / 127 / 341). The plan includes a small targeted task that edits `.planning/PROJECT.md` (`743` → live), `.planning/ROADMAP.md` (v1.3 section "214 + 127 = 341" → live, plus phase-detail count language), and `.planning/REQUIREMENTS.md` (COV-01 "341 chips covered" → live). Single commit, separate from the matrix-tool commits. SC-01 of the phase phrasing ("Total row count matches DB histogram (214 + 127 = 341 chips)") is updated to match — researcher / planner should note this is an in-phase amendment, not a defect against the matrix.
- **D-08: Numeric drift handled by the same tool.** The reconciliation section in the matrix is regenerated from the live DB on every run, so future DB regenerations (v1.4+) keep the reconciliation honest. If a future regen shifts counts again, the tool flags the new delta vs the matrix's last-committed counts — operator gets a re-reconcile prompt, not silent staleness.

### BENCH coverage proof depth

- **D-09: Three per-axis coverage tables.** Inside §5 of the matrix:
  - **Pinout-class coverage** — rows: each pinout class observed in §3 (DIP28_27256, DIP28_27512, DIP28_2764, DIP28_28C256, DIP28_28C64, DIP32_STD). Columns: row count, in-scope BENCH chip that exercises this pinout, "covered? Y/N", note if uncovered.
  - **Pulse-duration bucket coverage** — buckets: `<100 µs`, `100–999 µs`, `1–9 ms`, `10–99 ms`, `100 ms–1 s`. Per algorithm. Row count per bucket. In-scope BENCH chip whose `pulse_duration` falls into the bucket. Uncovered buckets called out.
  - **Size-bucket coverage** — sizes seen in §3 (2K, 8K, 16K, 32K, 64K, 128K, 256K, 512K, 1 MB). Per algorithm. BENCH chip that exercises each size. Uncovered sizes called out (so address-bus-span gaps are explicit).
- **D-10: Uncovered cells = explicit findings, not silent gaps.** Each uncovered cell in any of the three tables gets one line in §4 (DB Inconsistencies / Defect Candidates) **if** the gap reflects a structural concern, OR one line in §5's "Known Gaps" subsection **if** the gap is deliberate (e.g. v1.3 explicitly does not bench DIP28_28C64 because those rows are suspected mis-classifications — they show up in §4 as a separate finding). Lines cross-reference each other by ID.
- **D-11: Phase 11 stays observational on BENCH-05 / BENCH-06 selection.** The matrix's §5 must NOT propose a swap of BENCH-05 or BENCH-06 from the current REQUIREMENTS.md candidates (W27C257/W27E257/SST27SF256 for algo-0x07; W27C010/W27E010/W27L010/SST27SF010 for algo-0x08). It flags uncovered pinout classes (DIP28_28C64 = 35 algo-0x07 rows; DIP28_28C256 = 7 rows) and uncovered pulse buckets neutrally. Phase 12 CONTEXT.md owns the actual BENCH-05 / BENCH-06 selection — this matrix is the input, not the decision.

### Inconsistency taxonomy & defect IDs

- **D-12: Three severity tiers.** Every finding in §4 is tagged exactly one of:
  - **HAZARD** — Likely safety-relevant: 12V VPP routed to a 5V part, A14/VPP pin overlap, wrong erase strategy that risks the chip. e.g. the 42-row DIP28_28C64 + DIP28_28C256 + algo-0x07 + `UV-EPROM`-tag set is a HAZARD candidate (cousin of WARNING-5, which only caught the `electrical.type == Flash/EEPROM` subset on `DIP28_2764`).
  - **CORRECTNESS** — Likely programming-correctness, no damage risk: chips that share `pin_count` + `algorithm` but have different `pulse_duration`s in a range that suggests one is wrong (e.g. one chip at 100 µs and a near-identical part at 1,000,000 µs).
  - **VARIANCE** — Cosmetic / informational: `chip_id_check` toggled on/off across otherwise-identical rows; `chip_id_value` differing within an obviously-same-die family; manufacturer-spelling drift within one row's `part_number` comma list.
  - HAZARD-tier findings are listed first in §4; CORRECTNESS second; VARIANCE last. Counts per tier appear in §1 (Summary stats).
- **D-13: Stable IDs for every finding.** Each finding gets a `DEFECT-COV-NN` id starting at `DEFECT-COV-01`. The numbering is assigned at finding-creation time and persists across DB regenerations: the generator keeps a small `.planning/v1.3-defect-coverage-ids.json` ledger keyed by a stable finding-hash (severity + axis + grouping-key set) so that a re-run of the tool against a regenerated DB reuses the same `DEFECT-COV-NN` for any finding whose hash already exists, only minting new IDs for genuinely new findings. The ledger is committed alongside the matrix. v1.4 / sub-repo PRs reference findings by these stable IDs.
- **D-14: Per-finding metadata schema.** Each `DEFECT-COV-NN` carries: `severity` (HAZARD / CORRECTNESS / VARIANCE), `affected_chips` (integer count of DB rows + variant count if different), `axis` (the diverging field — `pulse_duration` / `chip_id_check` / `pinout` / `electrical.type` / a combined axis), `root_cause_hypothesis` (one line: upstream minipro classification vs real chip variance vs RURP-shield-specific vs unknown), `suggested_fix_venue` (one of: `v1.4 build_db.py override` / `v1.4 firmware handler` / `upstream minipro PR` / `awaiting bench data` / `documentation-only`), `examples` (up to 3 representative part_number/manufacturer pairs). The schema is rendered as a fixed markdown table per finding so the generator can do it deterministically.
- **D-15: The known WARNING-5 baseline.** The existing `build_db.py` `0x07 → 0x0D` override for `pinout == DIP28_2764 AND electrical.type == Flash/EEPROM` already neutralised one HAZARD class in v1.0 Phase 13. The matrix records this as a **resolved baseline finding** (e.g. `DEFECT-COV-00 — RESOLVED in v1.0 Phase 13`) so future readers see continuity, not as a fresh defect candidate. The 42 DIP28_28C64/DIP28_28C256 rows tagged `UV-EPROM` are a separate finding because they don't trip the existing override (`electrical.type != "Flash/EEPROM"` for them) — that's the new HAZARD candidate the matrix raises.

### Claude's Discretion

- **Exact bucket boundaries for pulse-duration coverage.** D-09 proposes `<100 µs / 100–999 µs / 1–9 ms / 10–99 ms / 100 ms–1 s` based on the observed live distribution (algo-0x07: dominant masses at 10 ms = 113, 100 ms = 28, 1 s = 28, 20 ms = 31; algo-0x08: dominant mass at 100 µs = 104). Researcher / planner may shift boundaries to better match the empirical clusters if a different bucketing makes the coverage gaps clearer; document the choice in §5's table caption.
- **Markdown table width / wrapping in §3.** The Full Enumeration table has ~9 columns and 339 rows. Render as one long table (operator scrolls) vs split per-algorithm (two tables stacked). Recommended: split per-algorithm so each table is narrower and the operator can jump to algo-0x08 quickly; both tables sort by the same key tree from D-06.
- **Ledger file format.** `.planning/v1.3-defect-coverage-ids.json` (D-13) — JSON dict mapping `finding_hash` → `DEFECT-COV-NN`. Researcher / planner picks the exact hash composition (suggest: sha1 of severity + axis + sorted tuple of (pinout, electrical.type, pulse_bucket, chip_id_check) signature). Stable enough that DB row additions don't shift existing IDs.
- **Renaming `chip_database.json`'s 743→734 drift root cause.** Some chips were probably dropped in v1.0 Phase 13 / v1.1 Phase 1 / v1.2 cleanup (e.g. the AT28C-family override-pivoted rows; or the SRAM-mistag fm1608 path). The reconciliation section can either dig into git-log on `chip_database.json` to attribute the delta, or just note "delta absorbed by v1.0–v1.2 overrides — see WARNING-5 + fm1608-db-mismatch". Recommended: short note, no archaeology — the matrix's job is forward-looking accuracy, not historical accounting.
- **Commit cadence.** Reasonable waves: (W1) `tools/audit_coverage_matrix.py` skeleton + summary-stats section; (W2) full-enumeration + grouping (D-06); (W3) defect-candidates §4 + ledger (D-12 / D-13); (W4) BENCH coverage §5 (D-09 / D-10); (W5) planning-doc count reconciliation (D-07) — last so it lands against final matrix numbers. Planner may merge waves; rationale above explains the dependency edges (each later wave consumes the earlier sections' computations).

## Existing Code Insights

### Reusable Assets

- **`firestarter_app/tools/check_dispatch.py`** — the exact loader/iterator scaffolding the new `tools/audit_coverage_matrix.py` mirrors. Lifting `_DATA_DIR` / `DB_FILE` / `FIRESTARTER_DB_FILE` env-var + the per-chip iteration pattern + the exit-code discipline saves implementation cost and inherits the conventions Phase 12 (v1.0) already validated. ~95 lines exist; the new tool will be similar size for §1–§3 + a longer §4 (defect-candidate analysis) + §5 (coverage tables).
- **`firestarter_app/firestarter/database.py::EpromDatabase`** singleton — already loads `chip_database.json` and exposes per-chip lookup. The new tool imports it the same way `check_dispatch.py` does. No new loader code needed.
- **`build_db.py` override constants** — `_PROTOCOL_OVERRIDES` etc. (lines ~130 + ~390) are the documented baseline for what's already-resolved (WARNING-5, fm1608). The matrix's `DEFECT-COV-00 — RESOLVED` baseline finding lifts that override list verbatim.
- **Markdown table conventions in `.planning/MILESTONES.md` + `.planning/phases/08-*/08-MEASUREMENT.md` (anchor table)** — both demonstrate the column-aligned 5–8-column table style that the matrix's §3 + §5 will reuse for visual consistency with the rest of `.planning/`.

### Established Patterns

- **DB iteration = manufacturer-keyed dict → list of chips.** Every existing DB-walking tool (`build_db.py`, `check_dispatch.py`, every host-side spec lookup) uses the same `for mfg, chips in db.items(): for c in chips:` shape. The new tool follows it.
- **`part_number` is a comma-joined variant string, not always single.** `W27C512,W27E512` is one row covering two part numbers. The matrix's summary stats expose **both** the row count (the audit unit — what `chip_database.json` actually stores) and the variant count (what an operator naming a chip would search by). Inconsistency findings count rows, not variants, because a row is one DB record.
- **Override semantics from `build_db.py:471`** — "the firmware dispatch is the ground truth". Phrased differently: an override applied in `build_db.py` is a data-layer fix; the firmware handler is never patched per-chip. The matrix's `suggested_fix_venue` field defaults to `v1.4 build_db.py override` for HAZARD findings unless there's a structural reason the data layer can't carry it.
- **Codegen idempotence rule** (Phase 06 Plan 06-01) — sort-by-stable-key + LF-only + no timestamps → byte-identical re-runs. D-02 inherits this. The new tool MUST pass a "run twice, diff zero" smoke test before the matrix gets committed.

### Integration Points

- **`chip_database.json` is the sole input.** No serial, no firmware, no infoic.xml. The matrix is purely a function of the committed DB.
- **`.planning/v1.3-COVERAGE-MATRIX.md` is the sole output** (plus the small `.planning/v1.3-defect-coverage-ids.json` ID ledger from D-13). No host-side runtime code consumes these files; they're operator-facing.
- **Planning-doc edits (D-07)** — `.planning/PROJECT.md`, `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md` are the side-effect targets. Targeted string-edits only (count fields); no structural changes.
- **The new tool does NOT touch the installed pip package** — it lives under `firestarter_app/tools/` like `check_dispatch.py` / `build_db.py`. `pyproject.toml` / `MANIFEST.in` already exclude `tools/` from the wheel; no packaging change required.

<specifics>
## Specific Ideas

- **"The matrix is the receipt for the milestone's claim."** Phase 11 isn't an artefact for its own sake — it's the receipt that, after Phases 12 + 13 ship green on the six BENCH chips, lets the operator state "and these six chips represent N=339 rows on axes X / Y / Z, with the following M defect candidates flagged for v1.4." The §5 BENCH coverage proof is the load-bearing section; §3 and §4 exist to support its conclusions.
- **DEFECT-COV-NN IDs survive DB regen.** The ledger (D-13) is a deliberate choice — it means a v1.4 sub-repo PR can reference `DEFECT-COV-07` and that ID will still resolve to the same finding when v1.4's chip-database update re-runs the tool. Anonymous enumeration would have broken that.
- **HAZARD-first reading order.** §4 sorts HAZARD findings before CORRECTNESS before VARIANCE — a v1.4 backlog grooming session reads top-down and prioritises naturally.
- **Phase 11 fixes its own DB-count discrepancy.** This is deliberate: the matrix would otherwise ship contradicting numbers against ROADMAP.md (the operator would have to mentally reconcile 341 vs 339 every time). The reconciliation section + planning-doc edit closes the loop in one phase.
- **Resolved-baseline finding (`DEFECT-COV-00`).** The existing v1.0 Phase 13 WARNING-5 override is recorded as the matrix's resolved baseline so the matrix carries continuity — readers see "yes, the project knew about this class of defect in v1.0; here are the new ones it didn't catch".

</specifics>
