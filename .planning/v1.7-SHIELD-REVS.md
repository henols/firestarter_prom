**Phase 35 ASCII correction (D-02 follow-through, post-Plan 01 INPUT high-Z fix):**

The original Phase 34 ASCII attributed `+5V VCC → MCU internal pull-up (Rpu = 20–50 kΩ)` as the R_top of a voltage divider, predicated on `pinMode(PIN_HW_REVISION_DETECT_ADC, INPUT_PULLUP)` at `firestarter/include/rurp_hw_rev_utils.h:43`. Phase 35 Plan 01 (CR-01 fix) **switched that pinMode to `INPUT` (high-Z)** for band-math correctness — which DISABLES the internal pull-up. The "divider" model is therefore invalid post-Plan 01; there is only R41 between A3 and GND (via JP4), and A3 reads ~0 V via ATmega ADC input leakage (~150 nA → ~3 mV across R41).

**Band-math semantics post-Plan 01:** the ADC bands now characterize *what's on the A3 net beyond R41*, not R41 value:

- **Stock Rev 2.0/2.1/2.2 (R41 to GND via JP4, nothing else):** A3 → ~0V → ADC ∈ [0, 200) → `REVISION_2_0` ("Rev 2.0-class"). R41 value is largely irrelevant to the detection outcome.
- **Modified Rev 0 (operator-attested rework — bench observation 2026-05-26):** A3 → ~1-3V → ADC ∈ [220, 600) → `REVISION_2_3`. The operator's mod has wired something between A3 and a positive rail, producing a mid-band reading.
- **Pre-Rev2 boards (no R41 designator):** A3 floats → variable / high ADC → `REVISION_0` or `REVISION_1` via the A2 disambiguation (preserved from prior code).

Empirical evidence: Phase 35 Wave 3 bench session (2026-05-26) — 5 boots × 3 boards = 15 reads, 100% stable, 0/15 reads in the `[200, 220)` guard gap. See `.planning/v1.7/bench-evidence-35.md` §"Band-math semantics under Plan 01 INPUT high-Z" for the full analysis. The existing `ADC_BAND_R41_*` threshold constants in `rurp_pinout.h:58-62` work empirically without modification; D-02 threshold widening per the original Phase 35 plan is no longer required.

**v1.8 substrate seed — Shield-Detection UX & Future-Rev Substrate:** three design directions surfaced post-R41-resolution (2026-05-26 — operator session); none gating on v1.7, parked as v1.8 backlog:

- **Option A — Reinstate INPUT_PULLUP (rejected).** Software-only revert to pre-Plan-01 divider math (internal Rpu as R_top). Works on typical Rpu≈30 kΩ boards (4k7→ADC 138; 10k→ADC 256) but the spec range Rpu=20–50 kΩ produces a 170–195 ADC overlap zone where 4k7 and 10k indistinguishable. **Rejected:** Plan 01 was the correct call; reverting reintroduces a class of "operator's MCU misclassified" bugs that the EEPROM override exists to mask. Honest broad-bucket detect beats a noisy auto-detect.
- **Option B — Future Rev 2.4 external R_top (deferred, additive).** Add a fixed `R_top = 10kΩ` from A3 to +5V on the next shield revision. Under INPUT high-Z this creates a real external divider: Rev 2.4-with-R41=4k7 → ADC≈327; Rev 2.4-with-R41=10k → ADC≈512 — clean 185-count gap regardless of MCU. Older stock boards still collapse to `REVISION_2_0` broad bucket → no regression. Firmware-side band-table extension can ship before Rev 2.4 PCB exists (additive). Gated on Anders-upstream Rev 2.4 spin (outside our control).
- **Option C — Operator-UX `firestarter rev --identify` (deferred, host-only).** Host CLI helper that prompts the operator with per-rev visual differentiators (JP4 1x2 vs 2x2 footprint, R41 color bands / SMD code, silkscreen letters) and writes the EEPROM byte. Firmware reports honest "Rev 2.0-class" + EEPROM-overridden silkscreen separately. ~half-day implementation in `firestarter_app`. Solves the **hard ambiguity** (Rev 2.2 vs Rev 2.3 — both R41=10k, physically indistinguishable from firmware perspective) and the **soft ambiguity** (Rev 2.0/2.1 vs Rev 2.2/2.3 — distinguishable in principle but unreliable under internal-pull-up variance).

**Physical limits** (regardless of which option ships): Rev 2.2 vs Rev 2.3 are *electrically isomorphic* at the detect divider (both R41=10kΩ to GND via JP4, only JP4 footprint differs 1x2 vs 2x2 — invisible to firmware). No software can disambiguate them; only operator visual inspection + EEPROM byte can. Document this clearly so future operators don't expect what physics can't deliver.

### JP4 Caveat

JP4 (silkscreen designator; alias `JMP_VPP_P1_BYPASS` per §7) carries P1_VPP_JMP — it's a jumper for routing VPP to socket pin 1, not strictly a "GND" pin. In the detect-divider topology, R41's lower terminal connects to one pin of JP4 such that the divider works only when JP4 is in a specific config; consult upstream Anders schematic (blob fe35bd78 on origin/Rev2.3, line 20582 for R41 + line 22562 for JP4) for the exact wiring. The footprint 1x2-vs-2x2 transition between Rev 2.2 and Rev 2.3 (mine-notes.md Finding D) is a physical-connector form-factor change but does NOT alter the electrical topology — both forms carry the same net.

**Phase 35 Wave 3 band footnote (D-02 follow-through):**

The firmware threshold constants ARE UNCHANGED post-Wave 3 because they work empirically:

- `ADC_BAND_R41_4K7_HIGH = 200` — upper edge of "R41-only-to-GND" low band. Empirical Phase 35: Rev 2.0 + Rev 2.2 land well below 200 across 10 fresh boots.
- `ADC_BAND_R41_10K_LOW  = 220` — lower edge of "A3-pulled-up" mid band. Empirical Phase 35: Modified Rev 0 (operator-reworked 10k pull-up) lands in this range across 5 reads.
- `ADC_BAND_R41_10K_HIGH = 600` — upper edge of mid band; above signals "A3 floating, no R41" (pre-Rev 2 era).

D-02 ("widen-after-bench-characterization") is satisfied **without** widening: the bench evidence shows 0/15 reads in the guard gap; the existing 20-count gap is empirically sufficient. The semantic interpretation of the bands has changed (A3-net composition, not R41 value), but the numerical thresholds are validated.

Wave 4 / v1.8 substrate seed: future Rev 2.4 PCB could re-introduce an external R_top resistor on the A3 net to make R41 value actually drive ADC variance and restore the original schematic-divider semantics. Until then, R41 value detection requires lift-leg measurement or visual marking inspection (out of firmware scope).
