Sentinel value conventions (use verbatim):
- "all" — rev supports the full chip-family list (UV-EPROM 28-pin, UV-EPROM 32-pin, AT28C EEPROM, AMD-style flash, Intel flash, SRAM)
- "as-modified — pending Phase 35" — Modified Rev 0 row across all capability columns where rework may have altered the baseline
- "TBD pending Phase 35" — Modified Rev 0 row across columns where rework trace is required
- "see notes" — when a capability claim needs supporting prose

## Cross-check contract (CAPS-02)

The capability matrix is cross-checked against firmware via automated grep:

1. Every `protocol_id` appearing in the `supported_protocol_ids` column of §6 MUST appear in `firestarter/src/proms/memory.cpp` as part of a `handle->protocol == 0xNN` comparison in `configure_memory`.
2. Every protocol_id in §6 MUST appear in `firestarter/CLAUDE.md` KNOWN_PROTOCOLS list (the documentation-of-record).
3. If a rev's `supported_protocol_ids` cell lists a protocol_id, the rev MUST have the physical capability (per the per-rev evidence table above) — i.e. a UV-EPROM protocol_id (0x07/0x08/0x0B) requires the rev to have a 12V VPP regulator path; SRAM/EEPROM (0x0D/0x0E/0x27/0x28/0x29) require only 5V VCC.
4. If a rev physically cannot support a protocol_id (e.g. Modified Rev 0 with rework-removed VPP regulator — hypothetical until Phase 35), that fact is captured in the `runtime_guard_gaps` column with a follow-up todo entry.

## §6 runtime-guard follow-up todos (appendix)

Per CAPS-02, when a rev physically cannot support an algorithm, a follow-up todo is captured for runtime-guard implementation in a later milestone. §6 carries an appendix block after the table titled `### Runtime-Guard Follow-Up Todos (out of scope for v1.7)` listing each per-rev gap with a description.
