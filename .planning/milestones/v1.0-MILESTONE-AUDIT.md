# Milestone v1.0 — Firestarter Protocol-Aware Programming Architecture

**Audited:** 2026-05-11 (re-audit after Phase 12 completion)
**Status:** GAPS_FOUND
**Score:** 4/18 requirements fully satisfied. 13 partial (verification-gap). 1 unsatisfied. 0 BLOCKER integration findings. 1 hazard-class E2E flow (AT28C256 write).
**Integration Report:** `.planning/INTEGRATION-CHECK.md` (post-Phase-12, regenerated 2026-05-11).

## Headline

Phase 12 closed both pre-existing BLOCKERs (BLOCKER-1 mem_type=2 fall-through;
BLOCKER-2 SRAM-routed-to-eprom hazard) end-to-end across firmware, Python host,
and the database pipeline. All four E2E flows that were broken (`write -e
W27C512`, `write -e AM29F040`, `erase -s 0x10000 -e SST39SF040`, `write -e 6116`)
now complete. The algorithm-first dispatch contract from PROJECT.md and
REQ-SER-01 is now structurally enforced for every entry in `KNOWN_PROTOCOLS`.

Two distinct gap classes remain:

1. **Verification artifacts** — Phases 01 through 10 still lack `VERIFICATION.md`
   files. By the workflow rule ("If a phase is missing VERIFICATION.md, flag it
   as 'unverified phase' — this is a blocker"), 10 of 12 phases remain
   structurally unverified. The integration check independently confirms the
   wiring is correct, and Phase 12's `check_dispatch.py` exercises every chip in
   the regenerated DB — but the formal goal-backward verification per phase has
   not been authored.

2. **Newly-elevated hazard (WARNING-5 escalated)** — The AT28C256/64 family (30
   chips with `algorithm=0x07` and `electrical.type="Flash/EEPROM"` in upstream
   minipro) previously hit BLOCKER-1 and produced a safe ERROR. After Phase 12
   the dispatch is "correct" by the contract (`algo=0x07 → configure_eprom`),
   but the upstream minipro classification of AT28C256 as EPROM_STD is
   semantically wrong: these are 5V EEPROMs whose socket pin 1 is `/WE`, not
   `VPP`. The `configure_eprom` path turns on `P1_VPP_ENABLE` during write,
   routing 12V to /WE. This is a hardware-damage path on writes (reads are
   safe). Phase 12 CONTEXT.md D5 explicitly deferred the per-chip override
   table; that deferral was reasonable when BLOCKER-1 guarded the entry, but is
   no longer safe.

3. **Pre-existing WARNINGs unchanged** — WARNING-1 (Intel-flash write path
   skips VPP ADC compare, breaking REQ-SAF-01 "for every chip"), WARNING-2
   (28C handler ignores chip_id, vacuous today), WARNING-3 (wire `"vpp"` key
   overloaded), WARNING-4 (test shell scripts reference deleted file). None
   of these were touched by Phase 12.

The PROJECT.md system-level contract is now substantially met at the dispatch
layer. The remaining concerns are (a) formal verification of phases 01–10,
(b) Intel-flash REQ-SAF-01 coverage, and (c) the AT28C256/64 active hazard.

## Cross-Phase Integration (Post-Phase-12)

### BLOCKERS

**None.** Both pre-existing BLOCKERs from the 2026-05-11T08:00 audit are closed
by Phase 12. See `INTEGRATION-CHECK.md` for the closure evidence trace.

### Closed by Phase 12

- **BLOCKER-1** (247 chips returning "Memory type 0x02 not supported") — closed
  via three-layer fix: `memory.cpp` protocol-prefix dispatch covering all
  KNOWN_PROTOCOLS (Plan 12-02), `database.py:_ALGO_MEM_TYPE` table driving
  `determined_type` from algorithm (Plan 12-03), `TYPE_FLASH_TYPE_2` constant
  deleted, regression scan `check_dispatch.py` PASS on full 743-chip DB.
- **BLOCKER-2** (52 SRAM chips routed to UV-EPROM handler with VPP regulator
  active on 5V parts) — closed via three-layer fix: firmware protocol-prefix
  dispatches SRAM protocols to `configure_sram` (a safe no-op stub) before the
  mem_type fallback can fire (Plan 12-02); `_ALGO_MEM_TYPE[0x0E/0x27/0x28/0x29]
  = 4` enforces `mem_type=4` on the wire (Plan 12-03); `build_db.py` emits
  `electrical.type="SRAM"` for these proto_ids (Plan 12-04).

### Cross-Phase Issues (remaining)

- **05 ↔ 03/07 (WARNING-1, UNCHANGED)** — `flash_intel_write_init` skips the
  ADC VPP compare. REQ-SAF-01 wording is "every chip"; the Intel-flash family
  (39 chips, 12V P1_VPP path) is the highest-VPP path in the firmware and
  violates this requirement. The UV-EPROM path satisfies it; the Intel-flash
  path does not.
- **06 ↔ 07 (WARNING-2, UNCHANGED)** — `eeprom_28c.cpp` ignores
  `handle->chip_id`. Vacuous today (zero 0x0D chips carry `chip_id_value`) but
  breaks REQ-SAF-02 the moment a user-override or DB change populates chip_id
  for an AT28C-family chip.
- **12 ↔ 06/03 (WARNING-5, ESCALATED)** — AT28C256/64 family (30 chips,
  algo=0x07, electrical.type='Flash/EEPROM') previously hit BLOCKER-1 and got a
  safe ERROR. Post-Phase-12 these route through `configure_eprom` →
  `eprom_write_init` → `eprom_write_execute` → `P1_VPP_ENABLE` on socket pin 1.
  On DIP28_2764 pinout AT28C256, pin 1 = /WE — applying 12V to /WE during a
  write pulse is a hardware-damage path. Requires a per-chip override table or
  a protocol guard.
- **11 ↔ 08 (WARNING-4, UNCHANGED)** — `firestarter_test.sh:31` and
  `write_test.sh:17` still reference deleted `database_generated.json`. Breaks
  the documented hardware-integration test E2E flow.
