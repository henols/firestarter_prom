# Cross-Phase Integration Check — Milestone v1.0 (Post-Phase-12 Re-Audit)

## Verdict: GAPS_FOUND

Phase 12 closed both pre-existing BLOCKERs (BLOCKER-1: 277 chips with unsupported
mem_type=2; BLOCKER-2: 52 SRAM chips routed to the UV-EPROM high-voltage handler).
All four E2E flows that were broken are now complete. The algorithm-first dispatch
is wired end-to-end across firmware, Python host, and the database pipeline.

One new integration gap was introduced by Phase 12: the AT28C256/64 family of 5V
EEPROMs (algo=0x07, 30 chips) was previously guarded by a safe ERROR exit (BLOCKER-1)
but now actively routes through `configure_eprom`, which applies 12V VPP to socket
pin 1 during write operations. On AT28C256/64 (which use DIP28_2764 pinout), socket
pin 1 = /WE — not VPP. Phase 12 CONTEXT.md explicitly deferred the AT28C256 mistag
(D5), but that deferral changed the failure mode from a safe ERROR to a potential
hardware damage path. Classified WARNING-5 with escalated severity.

The five pre-existing WARNINGs (Intel VPP ADC check, EEPROM chip_id ignored, wire
key naming, test-script drift, AT28C256 algo mistag) all remain. WARNING-5 is
re-classified from a documentation concern to an active write-path hazard.

## BLOCKERS

None. Both pre-existing BLOCKERs are closed by Phase 12.

### Closed: BLOCKER-1 — `_map_data()` mem_type=2 for Flash/EEPROM chips (CLOSED)

**Was:** `_map_data()` emitted `mem_type=2` (FLASH_TYPE_2) for chips with `electrical.type="Flash/EEPROM"`. Firmware `memory.cpp` had no `TYPE_FLASH_TYPE_2` dispatcher. 247/743 chips returned "Memory type 0x02 not supported" on write/verify/erase/blank.

**Fix (Phase 12):**
- Plan 02: `memory.cpp:configure_memory` now has protocol-prefix `if`-blocks for ALL KNOWN_PROTOCOLS before the mem_type fallback. `TYPE_FLASH_TYPE_2` constant deleted.
- Plan 03: `database.py:_ALGO_MEM_TYPE` table (13 entries) drives `determined_type` from algorithm; legacy substring branch preserved for `algorithm == 0` only.
- Plan 04: `build_db.py` emits `electrical.type = "SRAM"` for SRAM proto_ids; Flash/EEPROM and UV-EPROM tags unaffected.
- Plan 01: `check_dispatch.py` regression scan + Unity native tests (15/15 PASS) confirm all 743 chips dispatch correctly.

**Verification:** `python3 firestarter_app/tools/check_dispatch.py` → `PASS: all 743 chips have a valid dispatch path; 0 SRAM chips route to configure_eprom` (exit 0, live run confirmed).

### Closed: BLOCKER-2 — SRAM chips routed to `configure_eprom` (CLOSED)

**Was:** `build_db.py` emitted only `"Flash/EEPROM"` or `"UV-EPROM"` as `electrical.type`. SRAM/NVRAM chips (algo 0x0E/0x27/0x28/0x29) got `electrical.type="UV-EPROM"`, `mem_type=1`, and routed to `configure_eprom` which enabled `REGULATOR | VPE_TO_VPP` on 5V SRAM parts. 52 chips, hardware-stress hazard.

**Fix (Phase 12, three-layer defense-in-depth):**
- Plan 02 (firmware): SRAM protocols (0x0E/0x27/0x28/0x29) now reach `configure_sram` via protocol-prefix dispatch before the `mem_type == TYPE_EPROM` fallback.
- Plan 03 (Python host): `_ALGO_MEM_TYPE[0x0E]=4`, `[0x27]=4`, `[0x28]=4`, `[0x29]=4` — wire `type=4 (TYPE_SRAM)` even if `electrical.type` string is wrong.
- Plan 04 (DB pipeline): `build_db.py` emits `"type": "SRAM"` for `proto_id ∈ {0x0E, 0x27, 0x28, 0x29}`.

**Verification:** 52 SRAM-tagged chips in regenerated DB; zero SRAM-protocol chips tagged `UV-EPROM`; `check_dispatch.py` PASS; Unity tests for 0x0E/0x27/0x28/0x29 all PASS.

### WARNING-5 — AT28C-family EEPROMs with `algorithm=0x07`: failure mode changed from safe ERROR to active write-path hazard (SEVERITY ESCALATED by Phase 12)

**Affected REQ-IDs:** REQ-FW-03 (functional correctness), REQ-SAF-01 (VPP on wrong pin during write).

**What changed in Phase 12:** Before Phase 12, `AT28C256` (and related AT28C-family chips with `algo=0x07` and `electrical.type="Flash/EEPROM"`) hit BLOCKER-1: `mem_type=2` → `"Memory type 0x02 not supported"` ERROR. No hardware access occurred.

After Phase 12:
- `_ALGO_MEM_TYPE[0x07] = 1` (correct for UV-EPROM), so wire `type=1`.
- `memory.cpp` line 92: `protocol == 0x07` → `configure_eprom(handle)` via protocol-prefix.
- `configure_eprom` sets `firestarter_operation_init = eprom_write_init`, which calls `eprom_generic_init` → `eprom_check_vpp`. During write, `eprom_write_execute` → `program_mismatched_bytes` sets `VPE_ENABLE`. `eprom_internal_set_control_register` intercepts `VPE_ENABLE` and flips to `P1_VPP_ENABLE` when `using_p1_as_vpp(handle)` is true.

**For AT28C256:** `vpp-pin: 15` in bus-config (`0x0F = VPP_P1_28_DIP`), `pins=28`. `using_p1_as_vpp` returns `true`. `P1_VPP_ENABLE` routes 12V VPP to socket pin 1. On a chip using `DIP28_2764` pinout, socket pin 1 = VPP on a 27xx EPROM, but on AT28C256 (a 5V EEPROM), socket pin 1 = `/WE`. Applying 12V to `/WE` during a write pulse = pin damage.

**Scope:** 30 chips with `algo=0x07` and `electrical.type="Flash/EEPROM"`. This includes:
- AT28C256/64/64B/64E, AT28BV64/64B/256, AT28BV256 — confirmed 5V EEPROMs, no VPP needed.
- AT28C17/17E — older CMOS EEPROM family (some variants may legitimately accept higher voltage on a different pin; unclear from DB data alone).
- For `W27C512` (also `algo=0x07`, `electrical.type="Flash/EEPROM"`) — an electrically erasable UV-EPROM that DOES need 12V VPP: this path is CORRECT.

**Why not BLOCKER:** Phase 12 CONTEXT.md D5 explicitly deferred the per-chip override table as a separate future phase. The dispatch mechanism is correct for W27C512 and standard EPROM_STD chips. The AT28C256/64 mistag is an upstream minipro DB classification issue. Elevated from pre-Phase-12 documentation concern to active write-path hazard but scoped to a subset of chips. The safe failure mode (ERROR) has been removed; a future phase must add the AT28C256 override table or a protocol guard.

**User impact:** `firestarter write <bin> -e AT28C256` — previously: safe ERROR. Now: potentially applies 12V to socket pin 1 (/WE on AT28C256) during the write pulse. `firestarter read -e AT28C256` — safe (no VPP applied during reads).

## INFO

### INFO-1 — `pulse_delay=0` resolution in firmware

`convert_to_programmer` always emits `"pulse-delay": 0`. `eprom.cpp:configure_eprom` resolves defaults per protocol (0x08→100µs, 0x0B→500µs, default→1ms). Wired correctly and Phase 03 intent is preserved.

### INFO-2 — Phase 02 unknown-field skip works for nested objects

`json_parser.c:json_parse` and `parse_bus_config` both advance `token_idx += 2` on unknown keys, satisfying REQ-SER-02 in both the outer object and `bus-config` sub-object.

### INFO-3 — `static-high-pins` only populated for DIP24 variants

Only DIP24 variants list `static-high-pins` in `pinouts.json`. DIP28/DIP32 quirk pins (CE2, JEDEC-tied-high NC) could be added later. The firmware path is wired; only the DIP24 VCC-via-bus-line-13 case is exercised today.

### INFO-4 — `configure_sram()` is an intentional no-op stub

`firestarter/src/proms/sram.cpp:configure_sram` is 3 lines and does nothing beyond `debug("Configuring SRAM")`. It does not override any handlers. `configure_memory` sets generic `memory_read_execute`/`memory_write_execute` handlers before calling `configure_sram`, which is correct for SRAM (5V bus read/write, no VPP). The stub prevents the BLOCKER-2 hazard (no VPP regulator activation) while allowing read/write to proceed via the generic bus handler.

## Verdict

**GAPS_FOUND** — 0 BLOCKERs, 5 WARNINGs, 4 INFOs.

Phase 12 delivered its mandate. Both pre-existing BLOCKERs are closed end-to-end across
all three integration layers (firmware dispatch in `memory.cpp`, Python host `_map_data`
in `database.py`, data-pipeline in `build_db.py` and `minipro_complete_db.json`). All
four E2E flows that were BROKEN or DANGEROUS are now COMPLETE and SAFE:
- `firestarter write -e W27C512` → **COMPLETE**
- `firestarter write -e AM29F040` → **COMPLETE**
- `firestarter erase -s 0x10000 -e SST39SF040` → **COMPLETE**
- `firestarter write -e 6116` → **COMPLETE + SAFE** (was hardware-stress hazard)

One new integration concern surfaces from the Phase 12 changes: the CONTEXT.md D5
deferral of the AT28C256 per-chip override table changed the failure mode for 30
algo=0x07 Flash/EEPROM chips from a safe ERROR exit (BLOCKER-1 guarded) to an active
write-path route through `configure_eprom`. For AT28C256/64 family (5V EEPROMs that
do not require VPP), `configure_eprom` will apply 12V to socket pin 1 (= `/WE`) during
write pulses. This is WARNING-5 with escalated severity, not a new BLOCKER (the AT28C256
mistag in the upstream minipro DB is a pre-existing out-of-scope issue; Phase 12
CONTEXT.md explicitly deferred it to a future per-chip override table).

The milestone is **integration-complete for the primary target chip families** (UV-EPROM,
AMD Flash, Intel Flash, EEPROM_POLL, SRAM) but requires a follow-on phase to add
per-chip overrides for the AT28C256/64 family to restore the pre-Phase-12 safety gate.
