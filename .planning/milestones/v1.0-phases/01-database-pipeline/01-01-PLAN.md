<objective>
Fix parse_db_2.py to be a correct, lossless pipeline from minipro infoic.xml.

Purpose: This is the root cause of wrong algorithm selection. The current pipeline discards the authoritative protocol_id (converts it to a string then loses precision), stores VPP as an ambiguous string ("Unknown" causes silent 0V default), and uses a heuristic pinout resolver that was fixed in code but never run to rebuild the JSON.

Output: A corrected parse_db_2.py that produces entries with: integer `algorithm`, integer `vpp_mv`, correct `pinout` key, and skips unrecognized protocols with a logged warning.
</objective>

<task type="auto">
  <name>Task 2: Fix resolve_pinout_key() variant→pinout mapping</name>
  <files>firestarter_app/tools/parse_db_2.py</files>
  <action>
Fix `resolve_pinout_key()` to use an explicit variant lookup table instead of fragile if-chains. The correct mapping (from minipro ECOSYSTEM research) for DIP28 EPROMs:

```python
DIP28_VARIANT_MAP = {
    0x10: "DIP28_27512",   # 27C512 — VPP on pin 22 (OE pin), 19 address lines
    0x11: "DIP28_27256",   # 27C256 — VPP on pin 1, 15 address lines
    0x12: "DIP28_2764",    # 27C128
    0x13: "DIP28_2764",    # 27C64/2764A
}
```

Replace the 28-pin section of `resolve_pinout_key()`:
```python
if pin_count == 28:
    return DIP28_VARIANT_MAP.get(variant & 0xFF, "DIP28_2764")
```

For 24-pin, the existing variant==1 check for DIP24_2732 is correct — keep it.
For 32-pin, "DIP32_STD" is correct for all variants — keep it.

Also: validate that the returned pinout_key exists in the known pinout keys. Load pinouts.json at module startup and warn if a resolved key is missing:
```python
with open(PINOUT_FILE) as f:
    VALID_PINOUT_KEYS = set(json.load(f).keys())
```
In resolve_pinout_key, after computing the key, verify it's in VALID_PINOUT_KEYS (or None is OK — it means unsupported package).
