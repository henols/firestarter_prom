### 1. `firestarter_app/tools/build_db.py` — `_PROTOCOL_OVERRIDES` constant (add at module top)

**Analog 1 — `DIP28_VARIANT_MAP` (`build_db.py:93-98`):** The closest structural twin.
Same idiom: module-top dict, hex integer key, plain string or tuple value, underscore-prefix
for "internal" tables, defined in the numbered configuration block at the top of the file.

```python
# build_db.py:93-98  ← COPY THIS DICT SHAPE
DIP28_VARIANT_MAP = {
    0x10: "DIP28_27512",   # 27C512 — VPP on pin 22 (OE pin), 19 address lines
    0x11: "DIP28_27256",   # 27C256 — VPP on pin 1, 15 address lines
    0x12: "DIP28_2764",    # 27C128
    0x13: "DIP28_2764",    # 27C64/2764A
}
```

**Analog 2 — `VPP_MV` (`build_db.py:82-87`):** Shows the compact multiline dict style used for
denser tables where inline comments are unnecessary.

```python
# build_db.py:82-87
VPP_MV = {
    0x00: 12000, 0x10: 9000, 0x20: 9500, 0x30: 10000,
    0x40: 11000, 0x50: 11500, 0x60: 12500, 0x70: 13000,
    ...
}
```

**Analog 3 — `KNOWN_PROTOCOLS` (`build_db.py:89`):** Shows the simple set idiom when the value is
just membership.

```python
# build_db.py:89
KNOWN_PROTOCOLS = {0x05, 0x06, 0x07, 0x08, 0x0B, 0x0D, 0x0E, 0x10, 0x27, 0x28, 0x29, 0x35, 0x39}
```

**New `_PROTOCOL_OVERRIDES` shape — copy the `DIP28_VARIANT_MAP` naming and placement:**

- Name: `_PROTOCOL_OVERRIDES` (underscore prefix = internal, not exported via `KNOWN_PROTOCOLS` contract)
- Type: `dict[(manufacturer: str, name_prefix: str), dict]` — key is a 2-tuple because the
  discriminant is `(manufacturer AND name_prefix)`, not `protocol_id` alone.
  (W27C512 shares `algorithm=0x07` + `Flash/EEPROM` — only the AT28C family prefix distinguishes it.)
- Value: `{"algorithm": int, "electrical_type": str}` — the two fields that must be replaced.
- Placement: immediately after `KNOWN_PROTOCOLS` at line 89, before `VCC_VOLTAGES` at line 91.
  This keeps all "3. LOGIC MAPPERS" constants together.

**Skeleton (do NOT place `DIP28_VARIANT_MAP` style inline comments on value rows — use a block comment header instead):**

```python
# Per-chip protocol overrides for upstream-mistagged chips.
# Keyed by (manufacturer_name, part_number_prefix).  Applied AFTER reading
# the minipro XML record but BEFORE writing chip_entry, so build_db.py
# remains the single authoritative source of truth (REQ-DB-05).
# WARNING-5: AT28C/BV/LV family (5V parallel EEPROMs) are tagged
# algorithm=0x07 (EPROM_STD) upstream; they must route to 0x0D (EEPROM_POLL).
_PROTOCOL_OVERRIDES: dict[tuple[str, str], dict] = {
    ("ATMEL",            "AT28"):  {"algorithm": 0x0D, "electrical_type": "Flash/EEPROM"},
    ("MICROCHIP memory", "28C"):   {"algorithm": 0x0D, "electrical_type": "Flash/EEPROM"},
    ("MICROCHIP memory", "28LV"):  {"algorithm": 0x0D, "electrical_type": "Flash/EEPROM"},
    ("NEC",              "UPD28C"):{"algorithm": 0x0D, "electrical_type": "Flash/EEPROM"},
    ("XICOR",            "X28C"):  {"algorithm": 0x0D, "electrical_type": "Flash/EEPROM"},
}
```

**Style notes:**
- Hex literals with leading `0x` and zero-padded to two digits (matches `PROTOCOL_MAP`).
- One entry per line with consistent column alignment (matches `DIP28_VARIANT_MAP`).
- Block comment above the dict, not inline — matches `build_db.py` conventions for multi-line
  constant tables that need prose explanation.
- The type annotation `dict[tuple[str, str], dict]` matches the Python 3.9+ style used in the
  rest of the file (no `from __future__ import annotations` needed; the project already requires
  Python 3.9+ per `setup.cfg`).

**Scope note from live DB inspection:**
- 10 Atmel AT28x chips at `algo=0x07 + Flash/EEPROM` (AT28C256, AT28C64, AT28C64B, AT28C64E,
  AT28C17, AT28C17E, AT28BV64, AT28BV64B, AT28BV256/LV256, AT28PC64) — all need override.
- 7 Microchip 28C/28LV chips at same algo/type — same EEPROM family, same hazard.
- 2 NEC UPD28C chips — same hazard.
- 2 Xicor X28C chips — same hazard.
- W27C512, SST27SF512, SST27VF512 (WINBOND/SST, 27-prefix) — stay at 0x07; they genuinely need
  12V VPP on pin 1.
- AT28C chips already at algo=0x0D in the upstream DB (AT28C010, AT28C040, AT28LV010,
  AT28MC010/020/040) — not overridden (already correct).

### 2. `firestarter_app/tools/build_db.py` — override-application block (add inside chip-emit loop)

**Analog — SRAM detection block (`build_db.py:211-219`):**
This is the exact structural model. It sits between the last decoded field (`proto_id`, `flags`,
etc.) and the `chip_entry = { ... }` dict literal, and it computes a local variable (`_etype`)
that is then referenced inside `chip_entry`.

```python
# build_db.py:211-219  ← MIRROR THIS BLOCK'S SHAPE
# SRAM protocols emit electrical.type = "SRAM" (D4) ...
if proto_id in {0x0E, 0x27, 0x28, 0x29}:
    _etype = "SRAM"
elif flags & 0x10:
    _etype = "Flash/EEPROM"
else:
    _etype = "UV-EPROM"

chip_entry = {
    "part_number": name.split("@")[0],
    "electrical": {
        "type": _etype,           # ← local var consumed here
        ...
    },
    "programming": {
        "algorithm": proto_id,    # ← potentially mutated by override block
        ...
    },
    ...
}
```

**New override-application block — insert AFTER the `_etype` computation block (after line 219),
BEFORE `chip_entry = {` (line 221):**

```python
# Per-chip protocol overrides for upstream-mistagged families (WARNING-5).
# Checked AFTER _etype so the override can also change electrical_type if needed.
_override_proto = proto_id
_override_etype = _etype
for (ovr_mfg, ovr_prefix), ovr_vals in _PROTOCOL_OVERRIDES.items():
    if mfg_name == ovr_mfg and name.split("@")[0].startswith(ovr_prefix):
        _override_proto = ovr_vals["algorithm"]
        _override_etype = ovr_vals.get("electrical_type", _etype)
        print(
            f"  OVERRIDE: {mfg_name}/{name} "
            f"algo 0x{proto_id:02X}→0x{_override_proto:02X} "
            f"type {_etype!r}→{_override_etype!r}",
            file=sys.stderr,
        )
        break
```

Then inside `chip_entry`, replace the two hardcoded references:

```python
chip_entry = {
    ...
    "electrical": {
        "type": _override_etype,   # was _etype
        ...
    },
    "programming": {
        "algorithm": _override_proto,  # was proto_id
        ...
    },
    ...
}
```

**Style notes:**
- `print(..., file=sys.stderr)` matches the existing `WARN:` prints in the same function
  (`build_db.py:205`) — keep the same stderr channel for all diagnostic output.
- `break` after first match keeps O(1) behavior per chip; the override table is small.
- Variable names `_override_proto` / `_override_etype` follow the `_etype` underscore-local
  convention established by the SRAM block.
- The `for … break` pattern (not a dict lookup) handles prefix matching elegantly without
  needing a helper function.

### 3. `firestarter_app/tools/check_dispatch.py` — AT28C-family assertion (modify existing file)

**Analog — `_SRAM_PROTOCOLS` guard (`check_dispatch.py:49-52` + `check_dispatch.py:94-98`):**
The `_SRAM_PROTOCOLS` pattern is the exact model. It defines a named set at module top,
checks membership during the chip scan loop, accumulates violators into a separate list, and
reports them as a named failure category with the same `FAIL: N chips …` prefix.

**Module-top set constant (`check_dispatch.py:49-52`):**

```python
# SRAM protocol set — these MUST route to configure_sram, never configure_eprom
# (BLOCKER-2 electrical-safety; configure_eprom calls eprom_check_vpp which
# enables the VPP boost regulator on a 5V SRAM part).
_SRAM_PROTOCOLS = {0x0E, 0x27, 0x28, 0x29}
```

**Loop-body guard and violation collector (`check_dispatch.py:94-98`):**

```python
            # BLOCKER-2 safety: SRAM protocol must never resolve to configure_eprom
            if proto in _SRAM_PROTOCOLS and handler == "configure_eprom":
                sram_in_eprom.append(
                    f"{mfg}/{part} proto=0x{proto:02X} mem_type={mt}"

```

**New AT28C-family guard — mirror this shape exactly:**

Add a new module-top set and per-manufacturer override lookup dict:

```python
# AT28C-family chips that must route to configure_eeprom28c (not configure_eprom).
# WARNING-5: upstream minipro tags these as algorithm=0x07 (EPROM_STD); after the
# _PROTOCOL_OVERRIDES fix in build_db.py they emit algorithm=0x0D (EEPROM_POLL).
# This set names the manufacturer keys and prefix patterns from the override table.
_EEPROM28C_FAMILIES: dict[str, set[str]] = {
    "ATMEL":            {"AT28"},
    "MICROCHIP memory": {"28C", "28LV"},
    "NEC":              {"UPD28C"},
    "XICOR":            {"X28C"},
}
```

Add a violation list alongside `sram_in_eprom`:

```python
    eeprom28c_in_eprom = []
```

Add the inner loop check (after the BLOCKER-2 check):

```python
            # WARNING-5: AT28C-family must route to configure_eeprom28c, never configure_eprom
            prefixes = _EEPROM28C_FAMILIES.get(mfg, set())
            if any(part.startswith(p) for p in prefixes) and handler != "configure_eeprom28c":
                eeprom28c_in_eprom.append(
                    f"{mfg}/{part} proto=0x{proto:02X} routes to {handler!r} "
                    f"(expected configure_eeprom28c)"
                )
```

Add reporting in the failure block (mirror the `sram_in_eprom` reporting block exactly):

```python

            print(
                f"FAIL: {len(eeprom28c_in_eprom)} AT28C-family chips route to "
                f"configure_eprom instead of configure_eeprom28c (WARNING-5 hazard):"
            )
            for e in eeprom28c_in_eprom[:20]:
                print(f"  {e}")
            if len(eeprom28c_in_eprom) > 20:
                print(f"  ... and {len(eeprom28c_in_eprom) - 20} more")
```

Update the exit condition from:

```python

```

to:

```python

```

Update the `PASS` summary line to mention the AT28C check:

```python

        f"PASS: all {total} chips have a valid dispatch path; "
        f"0 SRAM chips route to configure_eprom; "
        f"0 AT28C-family chips route to configure_eprom"
    )
```

**Style notes:**
- `eeprom28c_in_eprom` list name mirrors `sram_in_eprom` naming convention (class + `_in_` +
  wrong handler).
- `_EEPROM28C_FAMILIES` uses the same underscore-prefix-module-top-constant convention as
  `_SRAM_PROTOCOLS`.
- The `any(part.startswith(p) for p in prefixes)` pattern handles both `AT28C256` (prefix `AT28`)
  and `AT28BV64` (same prefix) with a single set entry.
- The guard also catches the regression case: if `_PROTOCOL_OVERRIDES` is accidentally removed
  from `build_db.py` and the DB is regenerated with `algo=0x07`, those chips would appear here
  as violations.
- **Positive check, not negative:** The assertion is `handler != "configure_eeprom28c"` (must
  equal the right handler) rather than `handler == "configure_eprom"` — this catches any
  wrong dispatch, not just the specific EPROM path. This is slightly stricter than the
  `_SRAM_PROTOCOLS` pattern; the difference is intentional because the 0x0D dispatch is exact.

### 4. `firestarter_app/firestarter/data/minipro_complete_db.json` — intentional regen

**Analog — Phase 11 and Phase 12 regen pattern:**

Per Phase 12 CONTEXT D7 and Phase 12 PATTERNS section 4: the DB is regenerated by running
`python tools/build_db.py`. After Phase 13's `_PROTOCOL_OVERRIDES` block is applied, the
regenerated JSON will differ from the current file in exactly the chips overridden — their
`algorithm` fields change from `7` to `13` and their `electrical.type` fields stay `"Flash/EEPROM"`.

Verification approach (mirrors Phase 12 D7 JSON spot-checks):

```python
# Spot-check: AT28C256 must now have algorithm=13 (0x0D)
import json
db = json.load(open("firestarter_app/firestarter/data/minipro_complete_db.json"))
at28c256 = next(
    c for c in db["ATMEL"]
    if c["part_number"].startswith("AT28C256")
)
assert at28c256["programming"]["algorithm"] == 0x0D, \
    f"AT28C256 still at algo=0x{at28c256['programming']['algorithm']:02X}"

# Regression: W27C512 must remain algorithm=7 (unchanged)
w27c512 = next(c for c in db["WINBOND"] if c["part_number"] == "W27C512")
assert w27c512["programming"]["algorithm"] == 0x07, \
    f"W27C512 incorrectly overridden to algo=0x{w27c512['programming']['algorithm']:02X}"
```

**Expected diff shape:** approximately 20-30 chips change `"algorithm": 7` → `"algorithm": 13`.
The `electrical.type` field is left at `"Flash/EEPROM"` (correct — `0x10` bit in `info_flags`
must remain set; the info_flags derivation in `database.py:404-409` checks `electrical.type`,
not `algorithm`).

## Shared Patterns

### Pattern A — Module-top set/dict constant with underscore prefix (Python)

**Source:** `firestarter_app/tools/check_dispatch.py:49-52` (`_SRAM_PROTOCOLS`); also
`firestarter_app/tools/build_db.py:89` (`KNOWN_PROTOCOLS`); `firestarter_app/tools/build_db.py:82-87`
(`VPP_MV`); `firestarter_app/tools/build_db.py:93-98` (`DIP28_VARIANT_MAP`).

**Apply to:** `_PROTOCOL_OVERRIDES` in `build_db.py` and `_EEPROM28C_FAMILIES` in
`check_dispatch.py`.

Convention: underscore prefix for constants used only within the file; UPPER_CASE for constants
that may be referenced by sibling scripts.

### Pattern B — Conditional local variable computed before `chip_entry` dict literal

**Source:** `firestarter_app/tools/build_db.py:211-219` (the `_etype` SRAM-detection block).

**Apply to:** the override-application block in `build_db.py`.

Rule: compute all derived values into `_`-prefixed locals before the `chip_entry = { ... }`
dict literal, then reference the locals inside the dict. This keeps the dict literal flat and
readable.

### Pattern C — Named violation-collector list + threshold-truncated report

**Source:** `firestarter_app/tools/check_dispatch.py:78-117` (`errors` + `sram_in_eprom` lists,
`[:20]` truncation).

**Apply to:** `eeprom28c_in_eprom` list in `check_dispatch.py`.

Rule: one `list.append(f"...")` per violation in the loop; one `if list:` block in the
post-loop report section; truncate to 20 entries for readability on large DBs.

### Pattern D — stderr diagnostic output from build pipeline scripts

**Source:** `firestarter_app/tools/build_db.py:205` (`print(f"WARN: ...", file=sys.stderr)`).

**Apply to:** the `print("  OVERRIDE: ...", file=sys.stderr)` line in the override-application
block of `build_db.py`.

Rule: all diagnostic/warning output goes to `sys.stderr`; summary counts go to `sys.stdout`.
The `WARN:` and `OVERRIDE:` prefixes make the output greppable in CI logs.

## Key Observations for Planner

1. **AT28C scope is broader than the CONTEXT.md headline suggests.** The upstream DB contains
   not only `ATMEL/AT28C*` chips at `algo=0x07+Flash/EEPROM` but also `MICROCHIP memory/28C*`,
   `NEC/UPD28C*`, and `XICOR/X28C*` chips with the same hazardous classification (total ~20
   chips across 4 manufacturers). The `_PROTOCOL_OVERRIDES` table must cover all four families
   to close WARNING-5 completely. The CONTEXT.md "~30 chips" estimate was approximate; the
   current DB has ~21 chips needing override (10 ATMEL + 7 MICROCHIP + 2 NEC + 2 XICOR).

2. **AT28C chips already at `algo=0x0D` in the current DB do NOT need overriding.** The upstream
   minipro DB already correctly tags `AT28C010`, `AT28C040`, `AT28LV010`, `AT28MC010/020/040`
   with `algorithm=0x0D`. The override block uses `startswith` prefix matching keyed by
   manufacturer+prefix, so it must not accidentally re-override those already-correct chips.
   The loop checks `mfg_name == ovr_mfg and name.startswith(ovr_prefix)` and then sets
   `_override_proto` — but if the chip is already at `0x0D` the override would be a no-op
   (same value). Still, the print statement would fire misleadingly. Planner should add a
   guard: only apply and log the override when `proto_id != ovr_vals["algorithm"]`.

3. **`_SRAM_PROTOCOLS` guard in `check_dispatch.py` is the exact parallel structure.** The
   new AT28C assertion is a second instance of the same pattern: named protocol/family set at
   module top → membership check in loop → named violation collector → threshold-capped report.
   The planner can treat this as a copy-and-adapt operation with minimal invention.

4. **The `dispatch()` function in `check_dispatch.py` does not need to change.** The existing
   `if protocol == 0x0D: return "configure_eeprom28c"` branch already handles the post-override
   chips correctly. The new AT28C assertion only adds a check that chips from the override
   families actually reach that branch (i.e., their algorithm is now `0x0D` in the regenerated DB).

5. **`electrical.type` stays `"Flash/EEPROM"` after the override.** The `info_flags` derivation
   in `database.py:404-409` must keep `0x00000010` set for AT28C chips (they ARE electrically
   erasable — that bit is correct). Only the `algorithm` field is wrong in the upstream DB, not
   the `flags & 0x10` erasability bit. The override table should carry `"electrical_type":
   "Flash/EEPROM"` (unchanged) to make this explicit and auditable.
