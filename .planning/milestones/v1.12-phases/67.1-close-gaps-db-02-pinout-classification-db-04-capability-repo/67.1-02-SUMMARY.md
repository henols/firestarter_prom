# Phase 67.1 Plan 02: DB-04 Capability Reporting — CLI Surface Summary

Surfaced the `support_status` taxonomy to the operator through both the `info` display path and the chip-op refusal path. `firestarter info <non-supported-chip>` now renders a status-specific "Support status:" + "Reason:" warning line. `firestarter write/read/verify <non-supported-chip>` prints the DB's `unsupported_reason` verbatim (no generic prefix) and exits non-zero before any serial byte. A 6-test per-status CLI matrix (3 info + 3 refusal) pins the behavior for all three non-supported statuses.

## What Was Built

### Task 1 — DB-04 SC#1: Info Status Line (commit `92849df`)

**`eprom_info.py:prepare_detailed_eprom_data` — inject support_status:**

Added an injection block after `combined_data = eprom_specifications`. When `raw_config_data` is present and `support_status != "supported"`, sets `combined_data["support_status"]` and `combined_data["unsupported_reason"]`. Gated on the inequality so supported chips never receive the key (Pitfall 3 — avoids a "Support status: supported" line on W27C512 and all other supported chips).

**`eprom_info.py:present_eprom_details` — render status block:**

Added render block immediately after the Manufacturer line, gated on `chip_data.get("support_status")`. Uses `logger.warning` (operator caution level) with fixed-width alignment (`"Support status:      " + value`, `"Reason:              " + reason`). No f-string backslashes (Pitfall 4 compliance).

**3 new TDD tests in `test_cli_handlers.py` (caplog pattern):**

The `CliRunner` short-circuits `_setup_logging` when `ctx.obj` is pre-set, so `logger.warning` goes through pytest's caplog rather than CliRunner's output stream. All 3 tests use `caplog.at_level(logging.WARNING, logger="EpromConsolePresenter")` and assert on `" ".join(r.getMessage() for r in caplog.records)`.

- `test_info_vpp_exceeds_max_shows_status`: M2716 → exit 0, "Support status" + "exceeds" in caplog
- `test_info_adapter_required_shows_status`: AT28C16 → exit 0, "Support status" + "adapter" in caplog
- `test_info_protocol_not_impl_shows_status`: X88C64P → exit 0, "Support status" + "not implemented" in caplog

**Supported-chip regression guard:** `test_info_known_chip` (W27C512) snapshot passes — no new line rendered for supported chips.

### Task 2 — DB-04 SC#2/#4: Chip-Op Refusal + Per-Status Matrix (commit `3c5c3d7`)

**`cli_handlers.py:map_typed_errors` — drop "Chip not usable:" prefix:**

Changed `ChipNotImplementedError` arm from `raise click.ClickException(f"Chip not usable: {e}")` to `raise click.ClickException(str(e))`. Plan 01 reworded the `unsupported_reason` strings to begin with SC-required wording, so `str(e)` = `"<name>: <status-specific-reason>"` is the authoritative message. The arm remains AFTER the `ProtocolNotImplementedError` arm (subclass ordering preserved). Type-clean (watermark stays at 29).

**3 new per-status refusal tests:**

- `test_read_vpp_exceeds_max_status_refusal`: `read M2716 out.bin` → exit 1, "exceeds" in output, "Chip not usable:" NOT in output, no traceback
- `test_read_adapter_required_status_refusal`: `read AT28C16 out.bin` → exit 1, "adapter" in output, "Chip not usable:" NOT in output, no traceback
- `test_read_protocol_not_implemented_status_refusal`: `read X88C64P out.bin` → exit 1, "not implemented" in output, "Chip not usable:" NOT in output, no traceback

All 3 use `make_app_context()` with no eprom_operator — any serial I/O attempt would surface; the guard fires in `resolve_chip` before `convert_to_programmer`.

## Deviations from Plan

**1. [Rule 1 — Adjustment] caplog pattern instead of CliRunner.output for info tests**

- **Found during:** Task 1 implementation
- **Issue:** The plan spec says tests use `caplog/CliRunner pattern to capture logger output`. When `AppContext` is pre-built and passed via `obj=app`, the CLI group short-circuits `_setup_logging` (by design — WR-02 guard in cli_handlers.py:297-298). Without a logging handler, `logger.warning` records go to pytest's caplog interceptor, not to CliRunner's captured stream. `result.output` is empty even though the WARNING fires.
- **Fix:** Used `caplog.at_level(logging.WARNING, logger="EpromConsolePresenter")` context manager in each info-status test; asserted on `" ".join(r.getMessage() for r in caplog.records)` rather than `result.output`. This is the correct pytest pattern for capturing logger output from code that doesn't have `_setup_logging` active.
- **Files modified:** `tests/test_cli_handlers.py` (3 tests)
- **Commit:** `92849df`
