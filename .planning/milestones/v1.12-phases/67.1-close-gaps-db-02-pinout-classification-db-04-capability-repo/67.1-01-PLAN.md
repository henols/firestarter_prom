<objective>
Repair the DB build pipeline so the 14 native-SRAM DIP chips that currently fall through `resolve_pinout_key` to an EPROM pinout (DIP24_2716 / DIP28_2764) instead resolve to their correct SRAM pinout, and reword the three `unsupported_reason` strings so the host can render them verbatim as DB-04 status-specific messages (Approach A — DB is the single source of truth).

This plan owns ALL `chip_database.json` churn for the phase. DB-02 corrects 14 chips' `pinout` field (they stay `support_status: supported`). DB-04 Approach A reword changes the `unsupported_reason` text on the 14 non-supported chips (no `support_status` change). The two sets of chips are disjoint, so the regen is a single clean unit.

Purpose: Close DB-02 (no DIP-parallel chip silently mis-pinned for pinout reasons) and lay the DB source-of-truth string for DB-04 SC#2.
Output: Updated `build_db.py`, regenerated `chip_database.json`, expanded `test_build_db_inclusion.py`, all gates green.
</objective>

<decisions>
- **D-02 (DB-02 28-pin size discrimination): Option B — handle in the `build_db.py main()` loop**, in an adjacent block after the existing fm1608 override. Do NOT add a `mem_size` parameter to `resolve_pinout_key`. Rationale: parallels the existing fm1608 override pattern (which already sets `pinout_key` directly using `mem_size`), avoids a signature change to a function consumed elsewhere, and keeps all SRAM-pinout overrides co-located. (Research Open Question 2; research favors this.)
- **D-01 (DB-04 SC#2 message source): Approach A — the `unsupported_reason` strings in `build_db.py` are the single source of truth.** This plan rewords them to begin with the SC-required wording; Plan 02 prints them verbatim. Rationale: the DB string is read by BOTH the `info` display (DB-04 SC#1) and the chip-op refusal (DB-04 SC#2); one authoritative string avoids divergence. Accepts the DB-churn cost (handled here, in the same regen). (Research Open Question 1; research favors Approach A.)
</decisions>
