## Warnings

### WR-01: `vpp-exceeds-max` on combined entry refuses programmable CMOS variants

**File:** `firestarter_app/tools/build_db.py:632-650`
**Issue:** The INTEL combined entry `"2732,2732A,M2732,M2732A"` carries the NMOS
`M2732` alias, so the "highest VPP wins" loop tags the *entire* entry as
`vpp-exceeds-max` (25V) with `algorithm` demoted to `NON_DISPATCHABLE_ALGO`.
Consequence: a chip-op on the common, programmable CMOS parts that share this
entry (`2732`, `2732A` — both within the 22V ceiling) is now refused at
`resolve_chip` with `"VPP 25V exceeds programmer max (22V)"`. A user running
`firestarter read 2732` against a CMOS 2732 gets a hard refusal for a chip the
hardware can actually handle.

This is partially by-design (documented in the L46-56 comment: "operator must
override via ~/.firestarter/database.json"), and the NMOS block predates this
phase — but Plan 01's reword + the `info`-displays/`chip-op`-refuses split makes
the operator-facing impact sharper: `info 2732` shows the chip, but `read 2732`
refuses, and the only escape hatch is a manual DB override the average user will
not know to write.
**Fix:** Either (a) split the upstream combined alias so the CMOS variants get a
separate `supported` record, or (b) only demote `proto_id` to
`NON_DISPATCHABLE_ALGO` when *every* alias in the entry exceeds the ceiling, and
keep the entry dispatchable when it contains at least one in-ceiling variant
(downgrading the status to a softer "verify-vpp" note). At minimum, surface the
override instruction in the refusal `unsupported_reason` so the user has a
remediation path:
```python
_unsupported_reason = (
    f"VPP {_nmos_vpp_mv // 1000}V exceeds programmer max "
    f"({RURP_VPP_CEILING_MV // 1000}V) — if this is a CMOS variant, "
    f"override vpp_mv in ~/.firestarter/database.json"
)
```

### WR-02: info display surfaces no warning that a non-supported chip's pinout/VPP is misleading

**File:** `firestarter_app/firestarter/eprom_info.py:240-256`
**Issue:** For non-supported chips, `present_eprom_details` prints the
`Support status` / `Reason` block, then continues to print `VPP:`, `Type:`, and
the full DIP layout exactly as for a supported chip. For an `adapter-required`
24-pin EEPROM, the displayed pinout is `DIP24_2716` (the very wrong-for-EEPROM
pinout the reason string warns about: pin 21 mapped to 12V VPP). A user reading
the info output sees an authoritative-looking pinout that, if wired manually,
is the documented hardware-damage path. The reason text is the only thing
standing between the user and the hazard, and it is rendered at WARNING level
several lines above the layout.
**Fix:** When `support_status != "supported"`, either suppress the DIP-layout
block or annotate it with an inline caution (e.g., a one-line "pinout shown is
the RURP default and is NOT safe for this chip — see Reason above"). Keep the
electrical summary but flag the pinout specifically.

### WR-03: pre-existing lint failures in `build_db.py` (bare `except`, unsorted imports)

**File:** `firestarter_app/tools/build_db.py:310, 355, 1`
**Issue:** `ruff check` reports two `E722` bare-`except:` clauses (lines 310 and
355) and one `I001` unsorted-import-block (line 1). The bare `except:` at 355
swallows *all* exceptions during per-chip XML decode (including
`KeyboardInterrupt`/`SystemExit` in older idioms and any genuine logic error) and
silently `continue`s, so a malformed or unexpected `infoic.xml` row is dropped
with no diagnostic — masking DB-generation gaps. These are pre-existing (present
at base `807101e^`) and `tools/` may sit outside the CI ruff scope, but the file
is in this review's scope and the silent-drop behavior is a real robustness gap
for the DB pipeline.
**Fix:** Narrow both handlers and log the skip:
```python
try:
    ...
    type_int = int(ic.get("type"), 16)
except (TypeError, ValueError) as e:
    print(f"WARN: skipping {ic.get('name')!r} — unparseable attrs: {e}", file=sys.stderr)
    continue
```
Run `ruff check --fix` for the I001 import-sort.

## Info

### IN-01: stale docstring claims `"Chip not usable:"` prefix that this phase removed

**File:** `firestarter_app/tests/test_cli_handlers.py:255`
**Issue:** `test_read_non_supported_typed_refusal`'s docstring states the
`@map_typed_errors` decorator "converts ChipNotImplementedError -> exit 1 +
'Chip not usable:' message". This phase (cli_handlers.py:125-132) deliberately
dropped that prefix in favor of rendering `str(e)` verbatim. The test still
passes (it only asserts `"M2716" in output`), but the docstring now describes
behavior that no longer exists and contradicts the new tests at lines 856-898.
**Fix:** Update the line-255 docstring to match Approach A (reason string rendered
verbatim, no `"Chip not usable:"` prefix).

### IN-02: info `support_status` gate silently hides reason for falsy override values

**File:** `firestarter_app/firestarter/eprom_info.py:240`
**Issue:** The display gate `if chip_data.get("support_status"):` treats an empty
string as "supported/absent" and prints no block. A user-authored
`~/.firestarter/database.json` override with `"support_status": ""` (or any falsy
value) on a chip that also carries an `unsupported_reason` would suppress the
warning entirely. Low likelihood (requires a hand-malformed override), but the
injection side (`prepare_detailed_eprom_data:144`) and the display side use two
different truthiness models (`!= "supported"` vs plain truthiness), so they can
disagree.
**Fix:** Align both checks on the same predicate, e.g. inject only when
`ss not in ("", "supported")` and display when `chip_data.get("support_status")`
is non-empty — or normalize the status to `"supported"` when falsy at injection time.

### IN-03: dead `size_label` assignments in the Group 1 / 24-pin SRAM branch

**File:** `firestarter_app/tools/build_db.py:530-561`
**Issue:** In the `fm1608` block, the 28-pin branch sets `size_label` and uses it
in the subsequent `print(...)`, but the new 24-pin branch (`elif pin_count == 24`)
sets `pinout_key = "DIP24_6116"` and prints a message that does not reference
`size_label`. No bug — but `size_label` is a loop-scoped name reused across
iterations, so a stale value from a prior 28-pin chip could be referenced if a
future edit adds a `size_label` use to the 24-pin branch without assigning it.
Minor maintainability hazard given the variable's loop-level scope.
**Fix:** Keep the per-branch `size_label` assignment local to where it is consumed,
or initialize `size_label` to a known value at the top of each override branch.
