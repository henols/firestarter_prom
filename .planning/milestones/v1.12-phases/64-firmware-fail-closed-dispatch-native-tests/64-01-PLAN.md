<objective>
Make the firmware dispatch fail closed. Add a self-contained `configure_not_implemented()` handler (new translation unit) and wire it into `configure_memory()` so every non-zero unimplemented protocol receives an explicit `MSG_ERR_PROTOCOL_NOT_IMPLEMENTED` (0xBB) response with zero hardware side effects — closing the hazard where `protocol`=unknown + `mem_type=1` reaches `configure_eprom` and enables the 12V VPP regulator on a 5V part.

Purpose: Eliminate the silent VPP-hazard `mem_type` fallback path for non-zero protocols (the core safety value of v1.12).
Output: `not_implemented.h` + `not_implemented.cpp`, dispatch edits in `memory.cpp`, and an updated `firestarter/CLAUDE.md` Protocol Dispatch table.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host JSON → firmware `handle->protocol` | The `algorithm` field is parsed into `handle->protocol` by `json_parser.c`; a hand-crafted or buggy host can supply any 32-bit value, including unimplemented or infeasible protocol IDs. This is the only untrusted-input boundary in scope. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-64-01 | Tampering / Denial-of-Service (hardware) | `configure_memory()` mem_type fallback | mitigate | An unimplemented non-zero protocol with `mem_type=1` previously fell through to `configure_eprom`, enabling the 12V VPP regulator on a potentially 5V-only part (hardware-destruction hazard). Mitigated by the generic `handle->protocol != 0` guard routing to `configure_not_implemented` (zero hardware side effects, NULL op pointers) placed before the mem_type fallback. |
| T-64-02 | Tampering (hardware) | hand-crafted infeasible protocol `0x11`/`0x2A`/`0x2B`/`0x2C` | mitigate | FWH and GAL/PLD protocols a user might plausibly hand-craft are explicitly recognized via named arms routing to `configure_not_implemented` — documented infeasibility intent + no hardware side effects. Subsumed by T-64-01's generic guard but named for auditability (DISP-04). |
| T-64-03 | Spoofing / Repudiation | wire response | accept | `configure_not_implemented` reuses existing `RESPONSE_CODE_ERROR` and emits `MSG_ERR_PROTOCOL_NOT_IMPLEMENTED` (0xBB) carrying the offending protocol value, giving the host an explicit, decodable signal. No new response code; no new attack surface. |
| T-64-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this plan — pure C++ source edits in an existing PlatformIO project. No supply-chain surface introduced. |
