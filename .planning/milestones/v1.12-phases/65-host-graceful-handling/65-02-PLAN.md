<objective>
Phase 65-01 shipped the ProtocolNotImplementedError class, the Response.id field,
the _raise_for_error_response dispatch helper, and the "Unsupported protocol:"
arm in map_typed_errors — all internally correct and unit-tested. But verification
(65-VERIFICATION.md) found a STRUCTURAL PRODUCTION-PATH GAP: the 0xBB
MSG_ERR_PROTOCOL_NOT_IMPLEMENTED ERROR frame is emitted by the firmware during
command SETUP (inside init_programmer_framed, before the operation state machine
ever starts). On the host it is consumed by expect_ack() inside _probe_port at
connect time; expect_ack flattens it to (False, msg) and discards Response.id, so
_probe_port returns None, find_and_connect raises a generic ProgrammerNotFoundError,
and _setup_operation swallows that into (None, 0). The operator prints
"No compatible programmer found" and never reaches the correct "Unsupported
protocol:" CLI arm. SC#2 (HOST-01) is met only at unit level; SC#3 (HOST-02)
FAILS in production.

This plan wires the probe/connect boundary so the typed error reaches the CLI,
closes WR-02 (two MAIN-phase ERROR branches still bypass the dispatch helper),
and adds a MANDATORY integration test that drives the REAL path (no _execute_phase
shortcut, no operator.read_eprom side_effect injection).

Purpose: deliver the user-visible goal of HOST-02 on the actual wire path — an
operator running firestarter read/write against an unimplemented-protocol chip
sees an honest "Unsupported protocol: Protocol 0x.. not implemented — ..." message
and exit 1, distinguishable from a generic connect failure.
Output: a typed-raise inside expect_ack + propagation through _probe_port and
find_and_connect; WR-02 consistency fix in eprom_operations.py; a new
production-path integration test file.

HOST-ONLY (firestarter_app/ submodule). Builds ON TOP of 65-01 — does NOT modify
65-01-PLAN.md and reuses every asset 65-01 shipped (ProtocolNotImplementedError,
Response.id, _raise_for_error_response, the map_typed_errors arm).

## Approach decision: Option B (raise inside expect_ack), NOT Option A (thread id through the return arity)

Both options are grounded in 65-VERIFICATION.md "Suggested fix approach". This
plan chooses Option B for the following decisive reasons:

- Blast radius. Option A changes expect_ack's return arity from
  Tuple[bool, Optional[str]] to Tuple[bool, Optional[str], Optional[int]], which
  breaks 2-tuple unpacking at EVERY caller. A grep sweep finds 4 production call
  sites in serial_comm.py (~:625, :632, :680, :827), 5 in eprom_operations.py
  (~:1189, :1199, :1213, :1378, :1414), 4 in hardware.py (~:94, :148, :192 + a
  commented one), 1 in firmware.py (~:102) — AND four
  patch.object(SerialCommunicator, "expect_ack", return_value=(True, mock_msg))
  mocks in tests/test_fwguard.py (~:50, :77, :102, :133) that would silently
  return a 2-tuple while production code unpacks three. Option A is the larger,
  riskier change for a surgical gap fix.
- Surgical fit. Option B raises ProtocolNotImplementedError directly inside
  expect_ack when response.id == MSG_ERR_PROTOCOL_NOT_IMPLEMENTED, preserving the
  2-tuple signature for every other ERROR/OK path. Zero caller-unpacking changes.
  The typed exception simply propagates up once _probe_port and find_and_connect
  are taught to let it through (exactly as they already do for FirmwareOutdatedError).
- mypy-strict cleanliness. serial_comm.py is in the strict island. Keeping
  expect_ack's annotated return type unchanged avoids touching the typed return
  contract across all callers; we only add a raise branch.

Tradeoff acknowledged (the verifier's note): Option B couples a low-level
transport primitive (expect_ack) to a specific message id. Accepted as the lesser
cost — the coupling is a single, well-named, constant-keyed branch
(MSG_ERR_PROTOCOL_NOT_IMPLEMENTED imported, never literal 0xBB), and expect_ack
already special-cases response.type ("OK" vs "ERROR"), so id-discrimination on the
ERROR branch is a natural extension, not a new concern.
</objective>
