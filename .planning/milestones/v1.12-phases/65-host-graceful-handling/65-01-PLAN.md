<objective>
When the firmware emits MSG_ERR_PROTOCOL_NOT_IMPLEMENTED (0xBB, rendered
"Protocol 0x%02x not implemented", RESPONSE_CODE_ERROR — shipped in Phase 64),
the host must (HOST-01) raise a typed ProtocolNotImplementedError(EpromOperationError)
instead of a generic EpromOperationError, and (HOST-02) print a clear, actionable
CLI message that includes the protocol value and communicates
known-but-not-yet-supported, distinct from "Programmer error:".

This is the terminal host consumer of the 0xBB runtime error. HOST-ONLY
(firestarter_app/ submodule); pytest-provable with mocked/decoded responses,
no firmware and no bench required.

Purpose: close the fail-closed safety loop on the host side — an operator who
runs an operation against a chip whose protocol the firmware does not implement
gets an honest, distinguishable error instead of a cryptic "Programmer error".
Output: ProtocolNotImplementedError class, Response.id plumbing, centralized
id->typed-exception dispatch, the CLI arm, and a new pytest file covering the
4 cases from CONTEXT.md <specifics>.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| firmware → host (serial frame) | The 0xBB ERROR frame crosses here. It is already decoded/validated upstream (COBS + CRC8 transport, frame_parser id-frame decode) before this phase sees it. This phase adds no new transport, no new parsing of untrusted bytes — it reads an already-decoded `Response.id` (an integer) and an already-rendered `Response.message` (a string). |

No new external input, no auth/secrets surface, no DB reads, no filesystem or network I/O introduced by this phase. The only data crossing the boundary is the firmware-rendered error text and a one-byte message id, both already decoded by the existing frame parser.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-65-01 | Injection / Format-string | cli_handlers.py map_typed_errors ProtocolNotImplementedError arm | mitigate | The firmware-rendered text reaches the CLI via `f"Unsupported protocol: {e} — ..."` and is passed to `click.ClickException` as DATA, never used as a format template. No `%`/`.format()`/`f-string` is applied to the firmware text with it as the template, so a hostile `%`/`{}` in the text cannot trigger format-string evaluation. Verified by the verbatim-text CLI test (D-02: host does not re-parse or re-render the text). |
| T-65-02 | Tampering / Spoofing | a tampered serial frame forging a 0xBB id | accept | A device on the trusted serial link could already emit any ERROR; surfacing a forged "not implemented" message at most produces a misleading-but-non-destructive CLI error. Worst case is a false "Unsupported protocol" message — no hardware action, no privilege, no data loss. Transport integrity (CRC8) is owned by the v1.10 COBS layer, out of this phase's scope. |
| T-65-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this phase — all imports are intra-package (firestarter.exceptions, .frame_parser, .messages). No RESEARCH.md Package Legitimacy Audit required; no new dependency surface. |
</threat_model>
